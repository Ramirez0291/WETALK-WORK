## 范围与约束

**要做：**

- 项目目录与正式记录（来源卡、论断、作品版本），以及从 PPT 页面追溯到原文的链路；
- 提交入口（候选稿、晋升、崩溃恢复）、依赖索引与派生状态；
- DeepSeek API 适配器与用量记录；
- 三种工作方式：分工、竞争（密封起草＋选择＋移植补丁）、对抗核验（异议＋两步核验）；
- 规则调度：任务认领、依赖、租约、限流冷却；
- 任务包、阶段重置、观众型新读者；
- PPT 输出与成品检查。

**暂不做：** 检索库（Basic Memory）、Gemini Grounding 接入、编码任务支持、自动分工优化、多用户。

**技术约束：**

- 核心服务沿用 WETALK 的技术栈：Node.js 18+、原生模块、原生前端；
- 工坊仓库允许引入运行依赖（例如 PPT 导出），每个依赖在 README 里写明用途；WETALK 本体继续保持零依赖；
- 只监听本机，服务进程是正式区唯一的写入者；
- 结构化记录用 JSON，便于程序校验；长文本用 Markdown；
- Windows 优先，路径处理和命令行调用沿用现有的 Windows 兼容做法；
- 可调参数放在配置文件里；一致性要求作为系统不变量写在代码里，不提供开关；
- 工坊从 WETALK 派生为独立仓库，把 WETALK 设为 upstream 远程，按需同步修复；WETALK 不合入工坊功能。

WETALK 目前在 `main` 分支，共 4 次提交。工坊仓库从 WETALK 的 `main` 派生，保留提交历史。下表“本次改动”一列都只发生在工坊仓库里，WETALK 本身不改。

| 模块 | 现状 | 本次改动 |
| --- | --- | --- |

| `lib/store.mjs` | forum.json 整体重写；议题、发言、记忆本（按空间和参与者，带版本）、表决 | 不承载工坊记录，避免 forum.json 膨胀；工坊记录存在项目目录 |

| `public/` | 原生前端，含中英文 | 工坊页面作为主页面（`/`），研讨室移到 `/talk`；工坊页面有项目概况、任务、记录、追溯、提交与留档、待你决定 |
| `tests/` | 只有 i18n 测试 | 每个新模块补单元测试 |

有两点现成的设计可以直接利用：

- **调用本身是无状态的。** claude -p 和 codex exec --ephemeral 每次都是新会话，所以“阶段重置”几乎没有成本，关键在于提示词里装什么。
- **密封投票已经并行执行，并在服务端隐藏票面。** 竞争起草可以复用这套并行机制；但它只在接口层隐藏，票面仍会写进磁盘，所以要按契约四补上“密封期间不落盘”。

## 数据模型

正式记录只保存事实，状态一律由记录派生，不直接写入。这样即使中途崩溃，重启后全量重算也能得到一致的状态。

- **权威引用字段：** 论断的 `sources`、作品的 `claims`。`based_on` 由程序从这两个字段派生，Agent 不填写，也就不会出现“追溯链存在、失效传播却漏掉”的情况。
- **版本：** 每条正式记录带 `version`，引用一律写成 `{id, version}`。
- **内容寻址：** 所有输入内容（JSON、Markdown、来源正文、模板、skill）按内容 hash 存入 `archive/blobs/`，只增不改。记录和任务包通过 hash 引用它们。

| 实体 | 文件 | 关键字段 | 写入者 |
| --- | --- | --- | --- |
| 来源卡 | `sources/S###.json` | title、author、edition、citation 或 url、origin（最早可追溯出处）、text\_blob（正文快照）、retrieved\_at（快照时间）。可获取性不在来源卡里，见契约一 | 提交入口 |
| 论断 | `claims/C###.json` | type、text、sources（含 locator 与 quote）、earliest\_attestation（textual 必填） | 提交入口 |
| 核验记录 | `verifications/V###.json` | target（论断 id@version）、source\_versions、verdict、reason、support\_quote、verifier（Agent、模型、厂商，或你） | 提交入口 |
| 异议 | `objections/O###.json` | target、category、pointer、state、raised\_by、resolution | 提交入口 |
| 作品 | `outline/OL###` `script/SC###` `slides/SL###` | 页或节的 id、claims | 提交入口 |
| 内容来源 | 每条正式记录的每个版本都带 `provenance` | 主体类型（agent / human）、参与者、实际模型与厂商、task 与 attempt、判定依据、是否已证实 | 提交入口（从服务端保存的任务尝试和调用记录派生，不采信请求里自报的身份） |
| 候选稿 | `candidates/<sid>/`，sid = `<任务>-<尝试>-<时间>-<随机>`，主持人提交为 `H-<时间>-<随机>` | 结果内容、提交时的依赖版本、request\_id | 提交入口 |
| 任务 | `tasks/T###.json` | 见“契约三” | 调度程序 |
| 提交日志 | `_txn/` 与 `commits.jsonl` | 见“契约二” | 提交入口 |
| 事件 | `events.jsonl` | 仅用于审计，只追加 | 服务进程 |

**内容来源（provenance）。** 来源卡的 `author` 指文献作者，内容生产者另用 `provenance` 表示，避免同名混淆。它由提交入口从服务端保存的任务尝试、租约和调用记录派生，请求里自报的 author、model、vendor 一律不采信。重试或换模型时按新的尝试重新派生，不沿用旧身份。人类提交走受控入口，记为 human；MCP 外部会话绑定服务端登记的主体与租约，无法证实实际模型或厂商时记为 unverified，不能计入跨厂商的独立核验。人工编辑和移植补丁保留原内容的来源关系：来源、论断、作品带系统字段 `authors`（作者集合 = 各版本内容来源的并集，按主体类型＋参与者＋厂商去重：同一参与者换了厂商的模型，各次贡献都保留，推断不出厂商的那一项也一直保留（保守）；当前版本的内容来源一定在集合里；规则与抓取不算作者），由提交入口在晋升时填写，人工小改不会抹掉原作者。服务自己发起的调用报告了能推断厂商的模型时，这次尝试的身份以报告的厂商为准；与配置冲突时两者都记录（`configured_vendor`、`vendor_conflict`），作者与核验者两侧都用这同一个依据。竞争选定的方案写成作品时，内容来源是起草那次尝试的身份，另记选定者（选定者不算作者）；书记（规则）应用移植补丁写成的版本，作者集合并上被移植原文的起草者。规则与抓取不写进作者集合。人类核验如何计数在契约一里规定。

编号一旦出现在提交日志里就永不复用，记录文件被删掉也一样，旧的 `{id, version}` 引用不会被重新解释成另一条记录。核验记录与异议的写入规则（跨厂商、人类核验计数、异议状态机、核心结论的核验份数）属于契约一，自 WP5a 起经提交入口写入。核验记录的 `verifier`、异议的 `raised_by` 由提交入口按服务端认定的身份填写，提交内容里不能出现；异议的新版本沿用最初的提出者。核验记录只增不改。

**论断的派生状态**（每次读取时计算，提交者不能直接写）：

| 维度 | 取值 | 计算方式 |
| --- | --- | --- |
| 核验状态 | unreviewed / supported / disputed / unsupported，另附 independent（支持的独立核验者数）与 required（需要的份数） | 只计入绑定当前论断版本和当前来源版本、能计入份数的核验记录（见契约一），同一核验者只取最新一份：没有记录为 unreviewed；全部支持为 supported；全部不支持为 unsupported；判断不一致为 disputed |
| 版本新鲜度 | current / stale | 任一上游的当前版本高于 based\_on 里记录的版本，即为 stale |
| 未解决阻塞 | 异议编号列表 | 阻塞类异议中状态为 open、needs\_evidence、upheld 或 needs\_user 的 |
| 可进入成品 | 是 / 否 | 核验状态为 supported 且独立核验者数达到 required，新鲜度为 current，且没有未解决阻塞 |

由此得出四条规则：

- 来源更新只会让下游变成 stale 并要求重新核验，不会自动恢复可信；
- 论断修改后版本变化，旧核验不再计入，状态回到 unreviewed；
- 解除一个异议不影响其他异议；
- 崩溃发生在“写完新来源、还没标记下游”之间也没关系：新鲜度是算出来的，重启后下游自然是 stale。

**论断示例**（字段示意，尖括号内为占位；状态不在文件里）：

```json
{
  "id": "C007",
  "version": 2,
  "type": "textual",
  "text": "盘古开天辟地的故事，一般认为最早见于三国吴徐整的《三五历纪》。",
  "earliest_attestation": { "work": "《三五历纪》", "author": "徐整", "period": "三国·吴" },
  "sources": [{ "id": "S012", "version": 1, "locator": "<页码或章节>", "quote": "<原文引文>" }]
}
```

## 契约一：证据与核验

程序只检查指针有效，核验者判断证据是否支持结论。两步分开，各自留记录。

**第一步：指针是否有效（程序）**

| 指针 | 程序检查 | 能证明 | 不能证明 |
| --- | --- | --- | --- |
| quote | 引文出现在所引来源版本的正文快照中（晋升时检查，不通过就不能晋升） | 引文存在 | 引文支持目标结论 |
| fetch\_failure | Fetch 失败记录存在 | 这次获取失败 | 来源不存在，或原有结论错误 |
| missing\_source | 论断的 sources 为空 | 缺少来源关联 | — |

**引文定位规则：** 两边都去掉 Markdown 的标点转义（Fetch 返回的正文会把 `.` 写成 `\.`），并把连续空白压成一个空格；其余字符原样比较，全半角、繁简、标点差异都不归一。来源没有正文快照时，带引文的论断不能晋升。

**正文的来处：** 来源正文快照只有两个来处：Fetch 抓到的正文，或主持人在受控入口手工录入（例如纸质书，至少录入引文所在的段落）。Agent 不能直接写正文，搜索结果的 summary、snippet、content 都不能成为快照。两种快照都登记在 `snapshots.jsonl`，`text_blob` 只能指向登记过的快照（blob 目录里还有记录 JSON 等内容，存在不等于是正文）。

**第二步：是否支持（核验者）**

- 核验者读论断和来源正文（固定版本的快照），给出 supported 或 unsupported（含“证据不足”），并写理由。
- 判为 supported 时必须附支持引文。程序只检查这段引文存在；“是否支持”是核验者的判断，记录在案，可以被再次挑战。
- 核验者必须与论断作者分属不同厂商；核心结论默认需要两份独立核验。
- 核验记录绑定论断版本和来源版本，任一方升版后不再计入。
- **写入检查（晋升时）：** target 是论断的当前版本；source\_versions 正好是论断所引每个来源的当前版本；支持引文出自论断所引的来源并能在该版本正文快照里定位；核验者是作者集合中的一位、或与其中任一作者同厂商，一律拒绝（含同厂商的另一个模型、自报同厂商的 MCP 会话、原作者在主持人小改之后核验，以及主持人核验自己写过的论断）。核验记录只增不改，改判就另写一份。
- **份数：** 按核验者（主体类型＋参与者）去重，同一核验者只算最新一份；不同参与者各算一份，同厂商的两个参与者也各算一份（与作者都不同厂商时）。主持人算一份。身份未证实（MCP 外部会话）、推断不出核验者厂商、推断不出某位作者的厂商（核验者是主持人时除外）、实际报告的厂商与配置冲突（待确认）的记录保存但不计入，详情里列出原因。同一核验者的“最新一份”按编号的数值先后判断。核心结论（论断 `core: true`）需要 `verify.coreClaimVerifiers` 份，其他需要 `verify.otherClaimVerifiers` 份。
- **对抗核验任务（`verify_claim`）：** 输入内联论断、所引来源及正文；只派给能计入份数的核验者（不是作者集合中的一位、与每一位作者不同厂商、厂商推断得出、还没核验过当前版本）。结果是一个 JSON 对象（verdict、reason、support\_quote、objections），目标版本与来源版本取自任务输入，不采信回复里自填的版本。

**异议状态**

只有三类事实性异议会阻塞：来源不存在、数字错误、引文不支持结论。解释争议、叙事选择、可选扩展永不阻塞。

| 状态 | 进入条件 | 阻塞类是否阻塞 | 下一步 |
| --- | --- | --- | --- |
| open | 已提出，指针有效 | 是 | 由作者和提出者之外的核验者裁定 |
| needs\_evidence | 发现了问题（如数字前后矛盾），暂时定位不到原文 | 是 | 生成补证任务；超过次数上限转 needs\_user，不自动作废 |
| upheld | 核验者裁定异议成立 | 是 | 论断修改并重新核验后转 resolved |
| rejected | 核验者裁定异议不成立 | 否 | 提出者可以附新证据重新提出（另提一条） |
| needs\_user | 核验结论不一致，或对分类有争议 | 是 | 由你裁决 |
| withdrawn | 提出者撤回 | 否 | — |
| resolved | 成立的异议：目标已改版，新版本为 current 且核验份数够（作品与来源只要求已改版且 current） | 否 | — |

**转换与身份：** 新建只能是 open 或 needs\_evidence（后者只用于三类阻塞异议），且只能针对目标的当前版本。open → upheld / rejected 由裁定者执行：身份已证实（服务派发的任务或你），不是提出者，也不是作者集合中的一位；非主持人的裁定者与每一位作者的厂商都要推断得出且不同，报告与配置冲突的也不行（推断不出时不能由 Agent 裁定，可转 needs\_user）；必须写理由；open → needs\_user 由身份已证实的任何一方执行并写理由；needs\_evidence → open 由身份已证实的一方补上有效指针；needs\_evidence → needs\_user 由规则（补证次数用完）或你执行；upheld → resolved 由身份已证实的一方执行并写理由；open、needs\_evidence → withdrawn 只限提出者或你；needs\_user 只有你能裁决，唯一的例外是规则撤回自己因 gone 提出、来源已恢复的异议（只能转 withdrawn）。rejected、withdrawn、resolved 是终态。target 与 category 一经提出不能改，指针只在 needs\_evidence → open 时补上。

**指针：** quote（来源原文：引文在所指来源版本的正文快照里能定位）、fetch\_failure（带用量账本里那次抓取的记录号，须是针对该来源的失败抓取）、missing\_source（论断确实没有来源）、gone（只限规则，来源当前确为 gone）、location（只是位置描述）。三类阻塞异议提为 open 时指针必须能核对且对得上类别：来源不存在用 fetch\_failure / missing\_source / gone，数字错误与引文不支持结论用 quote；location 只用于 needs\_evidence 或不阻塞的类别。

**补证：** 异议处于 needs\_evidence 且没有进行中的补证任务时，规则生成补证任务（`find_evidence`），任务固定针对异议所指的目标版本（目标后来改版也一样，任务包附那个版本所引的来源与正文），每个任务只做一次，`evidence.maxAttempts` 按任务个数计；补证结果只能更新这条异议，找不到时这一次补证结束。用完仍待补证，规则把异议转为 needs\_user 并写明理由。

**来源可获取性**单独记录，不算异议，也不写进来源卡（否则 Fetch 失败会让来源升版、下游失效）。它由两份记录派生：主持人的确认（`availability.jsonl`），以及最近一次针对该来源的 Fetch 结果（用量账本）。主持人确认的 gone 优先，之后抓取成功也不改变，只能由主持人撤销；从没抓过的为 unknown。只认抓取地址与来源卡**当前（已提交）地址**相同的结果；主持人的确认同样带着确认时的地址，只对该地址有效。所以迁址失败、迁址抓取成功但晋升冲突，以及迁址前在途、迁址后才返回的旧地址请求，都不影响来源现地址的状态。

- available：正常；
- temporarily\_unavailable：Fetch 失败。保留已有快照，快照仍可作证据；按计划重试。没有快照的来源无法支持任何核验；
- gone：你确认来源已不存在。规则对每条（当前版本）引用它的论断提出“来源不存在”异议（open，指针 gone，提出者为规则）；你撤销确认时，规则撤回自己提出、还没结束、也没被裁定成立的这类异议；再次确认会再提，同一论断版本上已被驳回的不再重提。规则的写入同样经提交入口，身份为 system；每一项单独执行，某一条被拒不影响其余各条，错误在本轮结束后报告。

**验收案例**

- [ ] 来源写“没有证据表明 A 导致 B”，论断写“A 导致 B”：引文存在检查通过，但核验者判 unsupported，论断不能进入成品
- [ ] 论断改了措辞：旧核验不再计入，状态回到 unreviewed
- [ ] C07 有两条阻塞异议，只解决一条后仍不能进入成品
- [ ] 发现数字矛盾但找不到原文：异议为 needs\_evidence 并生成补证任务，超过上限后转 needs\_user
- [ ] Fetch 失败：来源标为 temporarily\_unavailable，已有快照仍可用于核验
- [ ] 与作者同厂商的核验记录被提交入口拒绝

## 契约二：提交与恢复

提交入口只做两件事：把结果收为候选稿；在串行的临界区里把候选稿晋升为正式版本。已完成的工作不会因为版本过期而丢掉，但过期的结果也不会直接发布。

**提交请求必须带：** request\_id（幂等用）、project、task\_id、attempt、lease\_token、每个被修改记录的 expected\_version、结果内容。

**两段处理：**

1. **收稿：** 校验格式、身份与租约（见契约三），存为候选稿。同一 request\_id 且内容相同，返回第一次的结果；内容不同，报冲突。
2. **晋升：** 进入仓库级串行队列（所有项目共用一个 git 仓库，所以队列也是仓库级的）。在临界区内依次检查：目标记录的当前版本等于 expected\_version；依赖全部为当前版本；通过验收规则。任一不满足，候选稿保留，返回原因，由任务基于新版本重做或复核后再晋升。

**晋升的写入顺序（写前日志）：**

1. 在 `_txn/<提交编号>/` 写清单：要写哪些文件、每个文件的新内容 blob、旧版本，状态为 prepared；
2. 把旧版本复制到归档；
3. 逐个文件先写临时文件再改名替换。Windows 上遇到文件被占用（EPERM / EBUSY）时重试；
4. 在 `commits.jsonl` 追加 applied 记录，这一行就是提交成功的标志；再追加审计事件；
5. 异步做 git 留档：只提交清单里的路径（按路径提交，不带上其他已暂存的改动），提交信息带提交编号、任务号和项目名。成功记 archived，失败记 archive\_failed 并进入重试队列。留档从 blob 取确切字节、用临时索引构造提交，不经过工作区；严格按提交编号顺序进行，前面没成功后面就等着。

**写入故障。** 清单落盘之后第 2–4 步出错（文件长期被占用、磁盘满等进程没有退出的情况），提交入口就地重做一次；仍然失败就进入写入故障状态，拒绝一切后续写入，直到重启时由恢复流程把这个事务做完。否则较早的失败事务会在之后被重做，覆盖掉中间已经确认成功的提交。applied 已经落盘之后的收尾出错，不影响提交成功。

**正式状态取已提交的快照。** 派生计算、追溯和晋升检查都按每条记录最后一次 applied 的 blob 读取，工作区文件只用来比对。被外部改过或删掉的记录照样按已提交的内容参与计算，但本身和全部下游都算 stale；它出现在目标或依赖链（含间接上游）里时，晋升被拒绝。从没提交过的文件不是正式记录。

**谁是事实来源：**

| 角色 | 内容 | 负责 |
| --- | --- | --- |
| 事实来源 | 正式记录文件＋`commits.jsonl` | 崩溃恢复只看它们 |
| 派生数据 | 依赖索引、新鲜度、核验状态、可进入成品 | 启动时全量重算，从不单独持久化为权威 |
| 审计 | `events.jsonl` | 只用于追查，不参与恢复 |
| 留档 | git | 只留历史，不参与恢复 |

**启动时的恢复规则：**

- `commits.jsonl` 末尾没有换行的一行：完整的 JSON 就补上换行保留，否则截掉；内存索引与磁盘采用同一个决定；
- 有 prepared 清单但 `commits.jsonl` 里没有 applied：按清单重做第 2–4 步。每一步都可以重复执行，完成后记 applied；
- 已 applied 但未 archived：重新排入 git 留档队列；
- 正式文件与最后一次 applied 清单的 hash 不一致（服务进程之外的改动）：记事件，进入“待你决定”。

**其他约定：**

- 界面上每次提交分开显示两个状态：数据已提交；留档已完成、待重试或失败。
- 内部流程（例如竞争）的候选稿带 `owner`，只能由该流程自己晋升；候选稿页面和 `/submissions/:sid/promote` 不能替它晋升，否则流程记录会不知道正式区里多了一个版本。
- 启动时在 projects 目录建锁文件（含进程号），发现已有存活的服务实例就拒绝启动。新建项目、晋升和 git 留档都经同一个仓库级队列，服务未运行时的命令行工具也要先取得这把锁。持有者已死时，接管必须跨进程互斥：以失效持有者的 token 为键排他地建接管目录，建成的一方再确认锁文件未变后原子替换；接管者死在半路时，下一位以它的 token 继续接管。
- projects 仓库忽略锁、临时文件、`_txn/`、`commits.jsonl`、审计事件、候选稿、旧版本副本和 blob 目录（已留档的正文快照照样被跟踪），以及任务文件 `tasks/`、竞争的流程记录 `competitions/`、调度状态 `workflow.json`、改动记录 `changelog.jsonl`、交接单 `handoff/`、冷却记录 `_cooldowns.json`（projects 根目录）、项目调用记录 `calls.jsonl`、任务包 `archive/packets/`、阶段记忆归档 `archive/memory/`、用量与可获取性账本、正文快照登记。git 只留正式记录的历史，不是完整备份：恢复项目要保留整个 projects 目录。
- git 留档按字面路径提交（`--literal-pathspecs`），项目名里的方括号等字符不会被当成通配，从而带上别的项目的改动；projects 仓库关闭换行转换（`core.autocrlf=false`），并由测试按字节核对留档内容与正式文件一致。

**验收案例**

- [ ] 两个任务都基于 C007 v2 修改：只有一个成为 v3，另一个保留为候选稿并返回版本冲突
- [ ] 写完新来源后强制杀进程：重启后，依赖它的论断和页面自动为 stale
- [ ] 在第 3 步中途崩溃：重启后补完写入，不出现半新半旧
- [ ] git 不可用：数据提交照常成功，留档显示待重试，git 恢复后自动补交
- [ ] 两个项目同时提交：各自的 git 提交只包含本次清单里的文件
- [ ] 尝试启动第二个服务实例：被拒绝

## 契约三：任务与租约

任务状态只由调度程序改变。租约防止两人同时做一件事，栅栏令牌防止旧执行者迟到，请求编号防止重传产生第二个结果。

**字段：** id、project、type、mode、inputs、depends\_on、state、attempt（当前尝试号）、holder、lease\_token（每次认领递增）、lease\_until、max\_attempts、depth（由提议链计算）、parent、budget\_used。工坊内部流程另附 competition（所属竞争）、sealed\_group（同组的密封任务）、division（分工的第几份），只由内部流程填写，接口请求体里的同名字段一律忽略。

**状态转换：**

| 从 | 到 | 触发 |
| --- | --- | --- |
| proposed | open | 类型在允许列表内，深度和预算未超限；否则转 needs\_user |
| open | claimed | 认领成功：attempt 加 1，生成新的 lease\_token |
| claimed | claimed | 持有者在租约内续租 |
| claimed | open | 租约到期未续租，或持有者主动释放；当前尝试记为 abandoned |
| claimed | submitted | 收稿成功，栅栏检查通过 |
| submitted | done | 候选稿晋升成功 |
| submitted | open | 晋升失败（版本过期等），需要基于新版本重做 |
| open | failed | 尝试次数达到上限；进入“待你决定”，不再自动重派 |
| 任一未完成状态 | cancelled | 你或规则取消；进行中的调用被中止，结果只存历史 |
| needs\_user | open 或 cancelled | 你决定 |
| claimed | submitted | 密封类任务（密封起草、匿名评审、观众型读者）：调用完成，结果只放进服务进程内存里的密封轮次 |
| submitted | done | 密封类任务：主持人揭晓该轮次，正文这时才写盘（揭晓规则见契约四） |
| submitted | open | 密封类任务：揭晓前服务重启，内存里的结果随之消失，本轮重跑（当前尝试记为 abandoned） |
| submitted | cancelled | 已交稿、尚未晋升的候选稿保留为历史，不再晋升（晋升前在队列里再查一次任务状态）；候选稿正在写入正式区时不能取消，写完后再处理 |

**同组的密封任务：** 竞争的几份方案（或同一轮的几份评审）带同一个 sealed\_group。派发其中任何一份时，同组还没结束的成员进同一个密封轮次，全部交稿后才能一起揭晓；服务重启后轮次随内存消失，再派发时按组重建。

**栅栏检查：** 只有同时满足“任务处于 claimed、lease\_token 是当前值、attempt 是当前尝试、租约未过期”的提交才能收稿。不满足的提交存为历史草稿，永不自动晋升。

**重启恢复：**

- 服务进程自己拉起的调用在重启后已不存在：这些任务的当前尝试记为 abandoned，任务回到 open；
- 通过 MCP 认领的外部会话可能仍在运行：它们的租约保持到期为止，可以继续续租。

**上限：** 每个项目的调用次数、API 费用、任务深度、单任务尝试次数都必须有上限，数值可调。超出后，新任务和重试都进入“待你决定”。API 调用内部的重试也计入调用次数；命令行 Agent（Claude、Codex）的每次调用同样占一个调用名额。每次物理请求发出之前，在同一个同步步骤里检查上限并占用一个调用名额（账本先写 start 行），结束后写 end 行结算，只结算不再计数。调用次数按 start 计，含进行中和中途退出未结算的尝试，是硬上限；费用按 end 结算，要等返回才知道，是软上限，超出量最多是并发在途请求的费用之和。

**验收案例**

- [ ] A 认领后卡住，租约过期；B 接手并提交成功；A 恢复后提交：A 的结果存为历史草稿，B 的结果不受影响
- [ ] 服务已接受结果但响应丢失，客户端用同一 request\_id 重试：返回第一次的结果，不产生第二个版本
- [ ] 同一 request\_id、内容不同：返回冲突
- [ ] 任务连续失败到上限：转 failed，不再循环
- [ ] 服务重启：服务自己调用的进行中任务被释放，可以重新认领
- [ ] 自动提议的子任务超过深度上限：进入“待你决定”，不自动执行

## 契约四：上下文与可见性

“只能写自己的目录”和“看不到别人的草稿”是两个要求。第二个要靠控制 Agent 实际能取得的上下文，而不只是在接口里隐藏。工具权限规则不等于操作系统沙箱，没有实测过的隔离不能宣称完成。

| 任务类型 | 输入方式 | 文件访问 |
| --- | --- | --- |
| 密封起草、匿名评审、观众型读者 | 固定任务包从标准输入传入，结果由服务端收集 | 无工具 |
| 读资料的任务（抽取、核验） | 任务包全部内联进提示词（Claude、Codex、DeepSeek），论断输入会附上它所引的每个来源（按引用版本）及正文快照；只有通用适配器（自带脚本）使用专用临时工作目录，只放允许的输入副本 | 无工具（实测：工作目录不构成隔离，见下） |
| 导出 | 幻灯片源＋模板＋skill 内容 | 只写自己的工作目录（WP7 实测） |

**实测结论（2026-10-18，Windows）：** 只开 Read / Glob / Grep、工作目录设为临时目录的 Claude 照样读到并列出了工作目录以外的文件，权限层没有拦截；Codex 只要开着 shell 就能读任何地方。所以工坊任务里的 Claude、Codex 一律不给工具，输入内联；不给工具的 Claude 在同样的授权测试里一个工具都执行不了。读资料任务若仍有命令执行记录（通用适配器等），按命令里的绝对路径、`..` 和 MCP 工具做越界检查，越界不予收稿；没查出越界只记为“隔离未证实”。

**各家的做法：**

- **Claude：** 全部工坊任务沿用 WETALK 现有的无工具调用（`--tools ""`、`--strict-mcp-config` 且不给配置），输入内联。原设计“读资料的任务只开放读类工具”经实测不能隔离，已放弃；JSON 输出里的 `permission_denials` 记进调用审计。
- **DeepSeek：** 走 API，本来就没有文件访问，只拿到任务包。
- **Codex：** 命令行 Agent 自带执行命令的能力。实测（2026-10-18，codex-cli 0.162）：只读沙箱能读工作目录之外的文件；用户配置里的 MCP 服务在 `exec` 下也会加载，可以作为另一条读取通道。全部工坊任务的调用一律加 `--ignore-user-config`（不加载用户配置里的 MCP 服务，显式传 `-m`），并关掉能关的全部工具：`shell_tool`、`unified_exec`、`apps`（内置应用，其中的 `search_service.web_run` 是网络搜索）、`plugins`、`remote_plugin`、`browser_use`、`computer_use`、`image_generation`、`tool_suggest`、`skill_search`、`multi_agent`、`goals`、`view_image`、`sleep_tool`，以及 `web_search="disabled"`；输入内联。实测之后仍剩协作类与“延迟暴露”的工具，关不干净，所以以 `--json` 事件审计为准：除 `agent_message` 与推理摘要之外，出现任何 item 类型（`command_execution`、`mcp_tool_call`、`file_change`、`web_search` 及以后新增的类型），该稿都标为“独立性未证明”，不参与本轮比较。审计依据是 Codex 自报的事件，两道防线都不等于操作系统级隔离；CLI 升级后要重跑实测探针。

**密封期间不落盘：** 草稿和原始回复只保存在服务进程内存里；调用记录先写去掉正文的占位，揭晓后再补写。占位里的审计只记独立性结论和工具事件、权限拒绝的数量，不记工具参数和被拒绝的输入（它们可能带着草稿内容）；调用失败时只记退出码，不记报错原文（报错里可能附有部分输出），工坊自己的报错和超时、中止、无法启动这几类除外。迟到的旧尝试（租约已过期或任务已被接手）的结果直接丢弃，不进密封轮次。这条占位规则覆盖所有持久出口：调用记录、任务历史、用量账本的结算行，以及 API 每次请求的报错（只留 parse、timeout 这类类别词或 HTTP 状态码，不留服务端报错原文和响应正文）。

**揭晓：** 先校验全部成员，任何正文写盘之前：已取消或失败的成员移出本轮，稿件丢弃、不落盘；其余成员必须是本轮收集、尝试号仍是当前的已交稿任务，有一个没就绪整轮就不动（返回 409 并列出原因）。然后逐项写盘（正文 blob、补写调用记录、任务完成），每一步都可以重做：中途失败时轮次和没写出的结果都保留，修好后对同一轮再次揭晓即从断点继续，不重复补写、不改动已完成的成员。全部写成后才从内存里释放本轮。服务若在揭晓前崩溃，本轮重跑。这样即使某个 Agent 能读整个磁盘，也读不到别人还在密封中的稿子。

**匿名评审：** 正文和元数据里都不出现作者、模型、厂商；用随机标签（方案甲、方案乙），对应关系只存在服务端，评审结束后公开。提交前由程序扫描正文里的署名并去掉。

**任务输入不带生产者身份：** 任何任务的输入里只放记录内容，内容生产者的身份字段（provenance、authors、verifier、raised\_by，含其中的模型与厂商）在组装任务包时一律结构化剔除；来源卡的文献作者（author）是书目信息，保留。匿名评审以这一步为准，正文署名替换与扫描作为补充；服务端的正式记录与归档照样保留完整的来源关系。

**观众型读者：** 只拿到讲稿或 PPT 文本，无工具；任务包里不含来源、论断、核验记录。输入只能是讲稿、大纲、幻灯片记录；blob 输入无法确认不含证据，新建任务和组装任务包时都拒绝。

**阶段重置的范围：** 每个“项目＋阶段”使用一个独立的 WETALK 记忆空间（现有功能支持从空间分支）。重置只归档并清空当前项目、当前阶段的工作记忆，不碰全局共享记忆和其他项目。先写归档（临时文件写完再改名），归档成功后才清空；归档失败时记忆原样保留，错误报给调用方，阶段不切换。切换是可以重做的操作：先把切换待办（交接单、旧阶段归档文件的位置）记进 `workflow.json`，再写交接单、归档并清空、建新空间、改阶段。中途失败时阶段不变、待办留着；再切换一次到同一阶段就从头重做，归档文件已存在时把空间里现有的记忆合并进去，不另起一份。待办没做完时不能切到别的阶段，调度暂停派发。

**交接单：** 阶段切换时由程序从正式记录、派生状态、竞争与最近几轮的记录生成，一页以内，不调用模型，不写内容生产者的身份（参与者、模型、厂商、主持人）。新阶段读资料任务和密封起草任务的任务包带上当前阶段的交接单（作为输入存档），不带此前的讨论；观众型读者（交接单里有论断计数）和匿名评审不带。

**验收案例**

- [ ] 密封起草期间，另一 Agent 的草稿不出现在任何文件、调用记录、归档、MCP 和 HTTP / SSE 中
- [ ] Codex 在密封任务中执行了读文件命令：该稿被标为“独立性未证明”
- [ ] 匿名评审实际发送的提示词里搜不到任何作者、模型、厂商名称
- [ ] 观众型读者实际发送的提示词里不含任何来源或论断
- [x] 工坊任务里的 Claude 没有任何可执行的工具：明确要求它读工作目录以外的文件时，工具调用不会执行、内容不会出现（Windows 实测；原案“只开读类工具、权限规则拒绝越界读取”实测未通过，已放弃）
- [ ] 重置某项目的一个阶段：全局记忆和其他项目的记忆空间不变

### WP3 DeepSeek 适配器

- `agents.mjs` 新增 `deepseek` 适配器：用 Node 自带的 fetch 调用 OpenAI 兼容接口；密钥只从环境变量 `DEEPSEEK_API_KEY` 读取；沿用现有的超时与中止。
- 重试：408、429、5xx 按退避重试；其他 4xx 不重试。重试计入项目调用上限。
- 用量：calls.jsonl 增加 `usage` 字段；Claude 适配器顺便记下 JSON 输出里已有的 modelUsage。
- `web.mjs`：封装 Search 与 Fetch；Search 结果只作线索，不存快照；Fetch 结果存为来源正文快照 blob，需要时经提交入口建立或更新来源卡；失败时来源（派生）为 temporarily\_unavailable，来源不升版，保留已有快照；遵守每秒 5 次的账户限速。
- `usage.mjs`：项目用量账本 `<项目>/usage.jsonl`，每一次物理请求（含失败与重试）两行：发送前的 start（占用名额）与结束后的 end（结算）；兼容读取第一版的单行格式（每行按一次已结算的尝试计数和计费，只读、不改写文件，重启不会重复计数）；调用次数与费用上限按它累计（见契约三“上限”）。来源可获取性由它（只看与来源卡地址绑定的抓取）和 `<项目>/availability.jsonl` 派生。两份账本不进 git。
- 账户限速按每次物理请求（含重试）执行，Search、Fetch 各一个限速器，所有项目共用；等待名额的时间计入总时限，可被中止。重试策略取每次逻辑调用时项目生效的 `retry`。
- `snapshots.mjs`：正文快照登记 `<项目>/snapshots.jsonl`。来源卡的 `text_blob` 只能指向登记过的快照：`fetch`（记录实际抓取地址、时间和服务，注明是第三方服务返回的 Markdown，不保证与网页逐字一致）或 `manual`（主持人录入，记录录入人）。

* [ ] 能调用并记录用量；超时能退出，“停止”能中断
* [ ] 用本地模拟服务器验证：429 和 5xx 会重试，400 不重试
* [ ] 搜索结果的 summary 或 snippet 不能作为引文进入论断

### WP4 任务契约与任务包

- `tasks.mjs`：按契约三实现状态转换、认领、续租、栅栏检查、幂等、取消、最大尝试、重启恢复、上限。不在 `modes` 里的特殊任务类型：`anonymous_review`、`audience_reader`、`export`，以及契约一的 `verify_claim`（对抗核验）与 `find_evidence`（补证，WP5a）。
- `packets.mjs`：任务包保存实际输入。每个输入（project.md、来源正文、记录、模板、skill）按内容 hash 引用 blob；同时保存实际发送的提示词和有效配置。hash 用来检查内容有没有变，不能代替内容本身。
- `visibility.mjs`：按契约四决定每类任务的输入方式和文件访问；密封期间的结果只存内存。
- 手动派发：通过接口或界面把任务派给指定 Agent，暂不自动调度。

* [ ] 契约三、契约四的全部验收案例
* [ ] 任一历史任务都能按任务包完整还原当时的输入。还原输入不等于重新运行会得到相同输出

### WP5 三种工作方式与核验

- `verify.mjs` 与 `objections.mjs`：按契约一实现两步核验、异议状态、补证任务、来源可获取性。
- **分工：** 拆成互不重叠的子任务，结果经提交入口汇总为来源卡和论断。互不重叠由程序检查：
  - 拆分时每项输入（记录或条目）恰好分到一份；
  - 晋升时子任务只能写自己那一份：一条记录指向的全部记录，都要在这一份的输入（论断输入连同它所引的来源）或本次新建的记录里，否则拒绝（`out_of_scope`）。“指向”包括引用（论断的来源、作品的论断）、核验与异议的目标、核验所读的来源版本与支持引文、异议指针里的来源（quote、fetch\_failure、gone）；
  - 新建的来源卡与已有来源同一地址，也拒绝（`duplicate_source`）；
  - 分到的条目整份作为任务输入（正文存成 blob，进任务包、内联进提示词），不放进 goal。条目最多 500 项、合计 20 万字，goal 最多 3000 字；超限在建任何任务之前拒绝，不截断。
- **竞争：** 密封起草（无工具）；匿名评审，每条意见指向具体的节、页或论断编号；由你选择（用表决功能投票以后再接）；落选方案里的保留内容写成移植补丁，逐条接受或拒绝，书记只应用通过的补丁。细则：
  - **标签：** 同组方案全部揭晓后统一分配随机标签，各轮评审用同一套；评审者不能是起草者；标签与起草者的对应关系在评审全部结束后公开。
  - **具体位置：** 某个方案的第几节，或该方案里出现、项目里存在的论断编号。节按 Markdown 标题划分：取最小的标题级别，它只出现一次又是第一个标题时取下一级；没有标题的方案全文算第 1 节；页按节计。指不到位置的意见退回，原文和原因保留；独立性未证明的评审整份退回。
  - **选定：** 由你进行并写理由。选定的方案原样写成正式作品（大纲或讲稿），内容来源是起草者，另记选定者。
  - **可引用论断：** 发起时按输入快照固定：输入里的论断，以及输入作品（大纲、讲稿、页面）引用的论断，版本一律按输入，不用当前最新版；同一论断在输入里出现两个版本时拒绝发起。作品正文和补丁搬来的原文里的论断编号（按完整编号匹配，两侧不能紧挨字母或数字），都要对得上可引用论断并按它绑定版本，对不上的明确拒绝，不静默省略。
  - **先记下、再提交、后补记：** 选定与书记先把要做的事记进竞争记录，再经提交入口晋升，晋升后补记结果。任何读取或操作之前，先按提交入口对这次请求的结果补齐：已晋升就补记；没收稿或晋升被拒就撤掉；收了稿却确认不了结果时保留，只允许原样重试同一个动作，其他会改竞争的操作一律拒绝。
  - **移植补丁：** 从落选方案搬运整节或其中逐字的一段，放到底稿某一节的前后、节首节尾，或整节替换；节号按底稿原来的分节。整节替换的那一节不能再有别的替换或节内插入。主持人或 MCP 会话（身份未证实）可以提出；接受或拒绝只限你，拒绝须写理由，决定后不改。
  - **书记：** 书记是规则，不调用模型。底稿加全部已接受补丁生成作品的新版本，底稿其余字符原样保留；只在自己上次写的版本上继续，作品在竞争之外被改过时不覆盖。“竞争之外的改动”指作品当前版本既不是书记上次写的那一版、内容来源里也没有记着这次竞争；竞争自己的提交不算。
  - **少数意见记录：** 被拒的补丁（含理由）、接受了但没应用的补丁、没被任何已接受补丁采纳的评审意见，以及落选方案原文。
- **对抗核验：** 由作者之外的厂商核验；核心结论默认两份独立核验。
- 提示词模板随 modes.mjs 维护。
- **研讨与工坊：** 研讨室的议题可以挂到项目上（`POST /api/threads` 带 `project`、可选的 `ref`；`GET /api/threads?project=` 按项目列出）。挂了项目的议题，记忆默认用这个项目自己的空间“工坊·项目名·研讨”；WP6 引入阶段后改为按阶段。

### WP6 自动调度与阶段重置

- `scheduler.mjs`：规则循环，只读规则，不调用模型做派发判断。派发前置条件已满足的任务；按分工表挑有工具、不在冷却中的 Agent；限流冷却；争议分流到补证任务或“待你决定”。细则：
  - **开关：** 自动调度按项目开关，默认关；另有“跑一轮”，只把当前已就绪的任务派一次。揭晓、选定、裁决这些决定不由调度做。
  - **轮：** 一轮 = 一批派发到全部结束。这批任务都不在进行中（已认领、已交稿等晋升）就收轮；密封任务交稿后等揭晓、尝试失败回到可认领，都算结束，后者下一轮再派。上一轮没结束时不开下一轮。
  - **挑参与者：** 指派了谁就派给谁；否则按分工表（任务类型对应到分工表的工作类型，值按参与者 id 或适配器名匹配，`different_vendor` 逐个试、资格不够的换下一位），跳过不可用、冷却中、手上已有进行中任务（`scheduler.maxPerParticipant`）的参与者；依赖没完成的不派；`offPeak.defer` 时高峰时段不派给 DeepSeek。没派出去的写明原因。自动调度一个都没派出去时也保存原因，和上次结果相同时不再写盘。
  - **冷却：** 按参与者记，所有项目共用，重启后仍在。API 被限流（429）按 Retry-After，没有就 `cooldown.apiSeconds`；命令行 Agent 报错里有额度用完或限流的字样时冷却 `cooldown.cliMinutes`（只在内存里判断，报错原文不落盘）。冷却只约束自动派发。
  - **上限：** 派发时超出调用次数或费用上限，任务转“待你决定”，这个项目这一轮不再往下派。已经到了上限时，自动调度一个都不再试，等你提高上限。
- 阶段重置：新阶段任务包不含此前的讨论；生成一页以内的交接单；记忆空间按契约四切换。阶段用七步流程（明确目标、收集来源、抽取论断、大纲、讲稿、幻灯片、审阅），由你切换，可以跳着或往回切；一轮还没收轮时不能切换。
- 讨论模式的长对话截断改为：项目约定＋决议摘要或交接单＋最近发言。具体为：工坊项目里的研讨，截断时用“项目约定＋当前阶段的交接单”代替开题帖；被省略部分里的表决结果作为决议摘要（最多 3 条）；别的研讨保留开题帖。截断后的总长不超过 `maxPromptChars`：背景最多占 35%，决议摘要最多占 20%（最多 3 条，每条只留开头并注明全文所在楼层），其余给最近发言；最近一条发言总会出现，太长时只留开头。挂到项目上的研讨，记忆默认用当前阶段的空间。
- 停滞检测区分三种情况：没填改动记录；内容没有变化（由程序比对得出）；有变化但质量指标没有提升（新增 supported 论断数、解除的阻塞数、观众型读者标出的不懂处数量）。后两种才算停滞，Agent 自报的改动类型只作辅助信号。细则：
  - **比对：** 收轮时与开轮前的快照比。内容按每条正式记录的正文比对，不看版本号与内容来源（只换了版本号、正文没变不算变化）。质量指标：支持且份数够的论断有没有新增；阻塞异议有没有解除；最近一次揭晓的观众型读者标出的不懂处有没有变少。
  - **另两种结论：** 没有任务完成、只有读者或评审（内容没变），都不算停滞。
  - **处理：** 连续 `plateau.rounds` 轮停滞时按 `plateau.action`：派观众型新读者读当前作品（有幻灯片读幻灯片，否则讲稿，再否则大纲；上一份还没结束时不再加），或交给你决定；没有作品可读时交给你决定。
  - **改动记录：** 读资料任务可以交 `{"changes":[…],"changelog":[{"id","type","note"}]}`，type 取 evidence / fix / clarity，新建的记录写临时编号；晋升后换成正式编号，只留这次真正写了的记录，记进 `changelog.jsonl`。观众型读者输出 JSON（restatement、confusions），不懂处才数得出来。

* [ ] 冷却期间不派任务；超出上限的新任务进入“待你决定”
* [ ] 三种停滞情况能被区分并分别记录

### WP7 导出与成品验收

- 幻灯片源：`slides/` 下每页一个记录，含标题、正文、讲者备注、引用的论断编号。
- 两种导出：Markdown（`export/markdown.mjs`）；PPTX（`export/pptx.py`，用 python-pptx 套用 .pptx 模板的版式）。Python 使用工坊仓库自己的 `.venv`，由 `export.python` 指定。
- 导出方式可配置：脚本导出，或派给指定 Agent（产物同样走提交入口和成品检查）；版式用模板文件或 skill 控制，它们的内容版本写进任务包。
- **结构检查（程序）：** 正文每个句子要么带论断编号，要么标为非事实；引用的论断全部“可进入成品”；字数不超上限；备注不为空；读回 PPTX 核对页数、备注和编号。
- **渲染检查：** PPTX → PDF 或图片 → 逐页检查文字溢出与重叠、字体缺失、图表标签裁切、图片变形 → 修复后重新验收。渲染优先用本机 PowerPoint（若已安装，由脚本自动化），否则用 LibreOffice 无界面模式。脚本列出 PPTX 用到的字体并对照本机字体。逐页视觉检查由多模态模型初查、你终审，结果作为核验记录保存。
- 试运行报告：四项指标与 WP1 基线逐项对比。

## 配置文件

配置只调参数，关不掉系统不变量。参数默认值写在 `workbench.defaults.json`，项目用自己的 `protocol.json` 覆盖；任务包记录实际生效的配置。

**系统不变量（写在代码里，没有开关）：**

- 目标版本检查（expected\_version）与依赖版本检查；
- 提交与身份、租约绑定（lease\_token、attempt），以及 request\_id 幂等；
- 引用完整性：based\_on 由程序派生；
- 状态由记录派生，提交者不能直接写状态；
- 核验者与论断作者分属不同厂商；三类事实性异议一律阻塞；
- 密封与匿名规则（契约四）；
- 调用次数、费用、任务深度、尝试次数必须有上限，数值可调，不能设为无限。

| `export.python` | 导出脚本使用的 Python 解释器 | 工坊仓库内的 `.venv\Scripts\python.exe` |
| `render.engine` | 渲染检查用的程序 | auto：有 PowerPoint 用 PowerPoint，否则 LibreOffice |

每次修改参数，在项目的 `decisions/` 里记一条：改了什么、为什么、依据哪次试运行的数据。

## 测试与验收

单元测试沿用 `node --test`，每个测试在临时目录里建小样本项目。时钟可注入，租约和冷却不用真等；提交流程的每一步之后都可以注入崩溃，再模拟重启。

| 模块 | 必测场景 |
| --- | --- |
| 派生状态（deps） | 多级 stale 传播；论断修改后旧核验失效；多条异议只解除一条仍阻塞；循环引用被拒绝 |
| 提交（txn、commit） | 契约二全部案例；每一步之后注入崩溃并恢复；改名遇到文件占用时重试 |
| 任务（tasks） | 契约三全部案例 |
| 核验（verify、objections） | 契约一全部案例 |
| 可见性与任务包 | 契约四全部案例；按任务包还原输入 |
| deepseek 适配器 | 用本地模拟服务器验证重试、超时、中止、用量记录 |
| 导出 | 结构检查；用故意做坏的样例验证渲染检查能查出问题 |

**集成测试：** 用一个固定样本项目（2 份来源、3 条论断、2 页幻灯片）走完整流程：提交、核验、追溯、更正来源、重新核验、导出、渲染检查。项目路径或用户目录含日文字符时，脚本和命令行调用也要跑通。

**试运行验收：** 同一主题、同一内容标准下，对比基线与多 Agent 版的四项指标，结果写进试运行报告。
