## R1 · P1 · 旧截图上的终审会被静默记到重新渲染后的新版本

位置：`lib/workbench/exports.mjs:346–354`；前端请求 `public/workbench.js:860`。

页面的终审 POST 只发送 verdict、note 和可选的 reviews，没有用户当前看到的导出版本、渲染目录或图片 hash。`finalReview()` 收到请求后重新读取当前导出，把当前版本和截图填进终审记录。晋升检查只能验证这份服务端刚填好的记录，无法知道用户看的其实是旧图。

复现（独立临时项目，真实生成 PPTX，假渲染器为两次渲染产生不同截图内容）：

1. 导出并渲染 EX001，页面读到 EX001@2 的两张截图。
2. 另一个操作重新渲染，EX001 变成 v3，图片 hash 改变。
3. 使用旧页面上“通过”按钮的同款请求体，对两页发送 `{ verdict: 'pass', note: 'Reviewed old version 2' }`。
4. 两条 RC 记录全部落到 **EX001@3 和新图片 hash**，最后 `deliverable=true`。

这在多标签页、断开 SSE、刷新尚未到达时均可能发生。模型初查按设计不是必需的，因此不能依靠可选的 `reviews` 引用保护；有旧初查编号时已有规则会拒绝版本不符，但没有初查的正常终审仍会发生以上问题。

影响：新一轮渲染本应要求重新逐页终审，旧图上的操作却能替未审的新图通过验收。

建议：终审请求必须携带用户看到的导出版本及渲染/图片标识；服务端在写记录时验证这些条件，版本变化返回 409 并要求刷新。不要在服务端将旧请求自动绑定到最新版本。保留晋升时的版本检查，覆盖“请求校验之后、晋升之前”再次变化的情况。

回归应同时覆盖：不做模型初查的旧标签页、带初查引用的旧标签页、请求与重新渲染交错、对同一当前截图正常改判。

## R2 · P2 · 外部会话认领视觉任务不带图片，却能产生计入初查的记录

位置：`lib/workbench/runner.mjs:148–157`；新 `visual` 模式通过 `visibilityOf()` 进入该既有认领分支。

服务端 dispatch 路径在 `execute()` 中为视觉任务提取图片、保存 attachments 并附给模型，但外部认领 `claimExternal()` 没有执行这些步骤，也没有拒绝 visual 类型。它只返回 `{ id, prompt }` 的任务包，保存的包中 attachments 为空。`POST /tasks/:id/claim` 可走到这个分支。

复现：

1. 为已渲染的两页导出建立视觉任务，模拟派发暂时不可用，使任务保持 open（使用服务的真实 requestReview 流程）。
2. 同一个被指派参与者以外部会话认领，认领成功。
3. 返回的 packet 只有 `id`、`prompt`；`restorePacket(...).attachments=[]`，没有任何图片附件。
4. 使用该有效租约和 task 内的页面绑定提交两条 initial/pass，晋升成功，导出视图显示 `visual.initial=2`。

任务元数据包含图片 hash，但 hash 不是已交付给会话的图片；该分支没有向模型提供可直接查看的图片输入，也没有把图片记进这次尝试的附件快照。仅有页面文字的输入不能完成要求的看截图初查。

影响：认领入口允许一条不满足视觉任务输入契约的执行路径，初查完成计数及任务包追溯会产生误导。此项**不会单独绕过主持人终审**，因此定为 P2。

建议：若本版只支持服务端调用视觉模型，就在 claimExternal 对 visual 直接拒绝，并保持任务可由服务端重试；若支持外部会话，则补齐图片交付、能力检查、任务包附件保存，并限制初查提交与这次任务绑定的页面一致。补真实认领入口的回归，不只验证 dispatch。
