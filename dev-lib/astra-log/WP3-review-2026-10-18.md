## R1 · P1 · 调用次数只在响应后累计，并发突破硬上限

位置：`lib/workbench/usage.mjs:55–74`；调用位置 `lib/workbench/deepseek.mjs:80`。

`beforeAttempt` 只检查已完成账本，直到 `onAttempt` 才增加 calls。多个在途调用都会看到相同的剩余额度，这不是原子的“检查并占用”。当前 Web 路由可以并发执行，账户限速器也允许 5 个首发请求同时进入。

复现：项目 `budget.calls=1`，本地模拟服务延迟 150ms 返回，同时调用 5 次 Search。结果：**5 次全部成功、上游收到 5 次、账本 calls=5、limits.calls=1**。

这与已批准的“费用软上限”无关，调用次数在文档中明确是硬上限。等待响应期间若服务退出，该次已经发送的尝试也尚未进入持久账本。

修复要求：每次实际尝试发出前，原子检查并预留/记录调用名额，完成后只结算该名额，不能重复计数。为重启后的未完成尝试保留保守记账。补测 calls=1 下的并发 Search、Fetch 混合请求、并发重试，以及发送后响应前退出；超过额度的调用必须在发送前被拦住。

## R2 · P1 · Fetch 更新来源时可把 B 的正文归到 A 的地址

位置：`lib/workbench/web.mjs:50–55, 80–83`。

传 `source_id` 时没有验证请求的 url 是否属于该来源；抓取使用请求 url，但晋升保留 `current.url ?? url`。于是请求 B 的正文可以写进 A 的来源卡，来源地址仍是 A。随后引用检查会在 B 的正文中通过，却向用户展示 A 的出处。

复现：先 Fetch `https://example.org/A` 建立 S001；再 Fetch `https://example.org/B`，同时传 `source_id:S001`。返回 fetchedUrl=B，但 S001 v2 的 url=A，text_blob 为 B 的快照。两个请求均成功。

修复要求：默认从来源自身地址抓取，或在请求显式给出不匹配地址时拒绝。若支持来源迁址，应有明确受控操作，更新实际抓取地址及来源关联，不能静默保留旧出处。对已关联来源的失败抓取也要使用同样的地址绑定，避免拿 B 的失败状态标记 A。补测不同 host、不同 path、来源无 URL、合法迁址和同 URL 更新。

## R3 · P2 · 只有首次逻辑调用限速，内部重试绕过账户 QPS

位置：`lib/workbench/web.mjs:30–32, 57–60`；`lib/workbench/deepseek.mjs:78–80`。

限速器位于调用 `client.search/fetchPage` 之前，只取得一次名额；客户端内部所有重试都不经过它。官方规定 Search 与 Fetch 各自按账户限制每秒 5 次，请求重试同样是实际请求。[官方 Search / Fetch 文档](https://api-docs.deepseek.com/guides/search/)

复现使用合法的全局零秒退避配置和本地 503 响应：同时 5 次 Search，前 5 个实际请求失败，随后重试成功；上游 **14–17ms 内收到 10 次请求**。现有测试只单独测 `createRateLimiter`，没有测带重试的 Web 调用。

修复要求：将账户限速放到每次物理请求之前，与预算名额检查协调。Search/Fetch 各自共享限速器，所有项目及重试都计入。同样让等待限速的时间受总超时/中止约束；当前等待在客户端 timeout 开始之前。补测并发首发与重试交错的时间窗口。

## R4 · P2 · 项目 `retry` 覆盖对 Web 调用无效

位置：`server.mjs:34`；`lib/workbench/web.mjs:32,60`。

共享客户端启动时固定使用 `WB_DEFAULTS.retry`，Web 调用只传 timeout 和 usage hooks，没有传项目的生效 retry。`protocol.json` 允许覆盖 `retry.max`、`retry.delaysSec`，但实际执行完全忽略它们。

复现：项目配置 `retry.max=0`，读取 config 确认为 0；模拟服务先返回 503，再成功。Search 发出 **2 个请求并成功**，而不是在第一次失败后停止。

修复要求：每次逻辑调用读取并快照项目有效重试策略，传入客户端；避免修改共享客户端的全局可变配置导致项目间串扰。账户级 baseUrl、价目及 QPS 仍共享。补测两个项目同时使用不同重试次数/间隔，且项目禁止重试时 503 只发一次。

## R5 · P2 · 收到 200 头后正文断连，被错归为 parse 且不重试

位置：`lib/workbench/deepseek.mjs:99–111`。

`res.text()` 抛网络错误时保留了 `res`，catch 设置 `networkError`，但后续仍因为 `res.ok` 进入成功分支。此时 text 未赋值，是空字符串，最终抛 parse 错误；应走的网络重试分支从未执行。

复现采用真实本机 HTTP 服务：先发 200 和保活换行，30ms 后断开连接；如果客户端重试，下一次返回正常 JSON。实际只收到 **1 次请求，错误 kind=parse**。这与 DeepSeek 非流式调用先发空行保活的运行方式直接相关。

修复要求：先处理读取正文的网络异常，只有完整读取成功才按状态码解析。断连按现有网络重试策略处理并记录一次失败尝试；真正完整返回的非法 JSON 仍可作为 parse 错误。补测保活后断连、非 200 正文断连、超时/用户中止（后两者不得误重试）。

## R6 · P2 · Fetch 无正文返回失败，却把来源标为 available

位置：`lib/workbench/deepseek.mjs:113`、`lib/workbench/web.mjs:69`、`lib/workbench/usage.mjs:105`。

HTTP 200 JSON 被通用客户端先记成 `ok:true`；随后 Web 层才检查正文是否为空并抛 404。availability 只看账本中的 ok，因此该失败抓取反而恢复来源可用状态，也没有可供以后 `fetch_failure` 指针使用的正确失败记录。

复现：S001 先抓取成功，再 404 变成 temporarily_unavailable；下一次模拟响应为 `{title:"fixture page",content:""}`。Web 接口对应调用返回 404，而来源变成 **available**；最后账本行是 `ok:true,status:200,usd:0`。

修复要求：把 HTTP 状态与“得到可用正文”的业务结果区分开，最终一次尝试记账应包含实际抓取结果；空正文/响应结构不合法不能成为可用性恢复依据。保持失败不升来源版本、旧快照仍可核对引文。补测空正文、缺 content、错误 content 类型，核对 HTTP 结果、账本、可获取性三者一致。

## 回应 WP3 设计问题

### 可获取性移出来源卡

认可，且主持人已批准文档修订：抓取失败是访问状况变化，不应自动让已有证据快照升版。将 gone 保留为主持人的明确确认也合理。R2、R6 需要先修复，确保派生事件关联正确来源、记录真实结果。WP5 接入 gone 自动异议时还需处理重复确认与撤销，避免生成重复阻塞。

### 晋升时检查 quote

认可；它证明指针存在，不证明支持结论。纸质书录入引文所在段落可以使用，应一并保留书目信息与页码，不能让“仅有局部摘录”被误解为已获取整本文献。现有 Markdown 转义/空白规范化与文档一致。

WP4 开放真实 Agent 提交前，需再验收 `text_blob` 的来源约束：当前仅检查 hash 在通用 blobStore 中存在，该目录同时保存记录 JSON 等内容，存在不等于它就是 Fetch/主持人登记的正文。建议为正文快照保存可校验的来源类型和原始 URL/录入主体，避免未来通过任意已有 blob 绕过 `text` 的身份限制。本轮没有把尚未开放的 Agent 提交通道列为已发生的漏洞。

### 软费用上限

主持人已同意，可继续采用，不必本轮改成严格的 `max_tokens` 预留成本。先修复 R1；有并发时“只最后一次略超”并不成立，必须说明在途请求的影响，或设置并发/在途费用约束。若以后需要硬费用上限，再结合输入 token、输出上限及最坏价格预留，不能只预留输出部分。

### Fetch 返回了服务端加工内容

保留原始 Fetch 响应快照、时间和实际 URL；任务包注明它是第三方 Fetch 返回的 Markdown，不能声称与网页逐字一致。核验者应区分正文与服务端加入的说明。无需把泛化风险提示重复写入每段最终内容；对关键引文确有差异时再回查原页面或原始文献。
