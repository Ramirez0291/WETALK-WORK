## 2. 幻灯片源的约定

`slides/` 下每页一条记录，字段有 title、body、notes、order、claims，按 order 再按编号排序。正文的约定：

- 每个句子要么带论断编号，要么标为非事实。
  - 编号写 `C001`，可以单写，也可以写在〔〕［］[]（）() 里；几个编号用顿号或逗号隔开。
  - 非事实写 `〔非事实〕`，放在句首或句尾。
  - 句末标点后面紧跟的编号（`……。（C001）`）算前一句的。
- 编号必须在这一页的 `claims` 里，按那里写的版本绑定。
- `- ` 开头的行是要点，缩进两格是下一级。
- 导出时，编号和标记都从页面上去掉。PPTX 里，编号挪进讲者备注：备注后面加上“依据”（每条论断的原文摘要）和一行标记 `〔SL001@1 · 依据 C001@1、C002@1〕`。Markdown 里，编号写成脚注。

## 3. 导出记录 `EX###`

- 每次导出写成一条正式记录 `exports/EX###.json`，经提交入口晋升。写入身份是规则 `workbench-export`，主持人入口和任务提交都写不了（403）。
- 记录里有：
  - 用了哪些幻灯片（`{id, version}`）；
  - 模板和 skill（文件名＋内容 blob）；
  - 版式方案、出方案的任务与尝试；
  - 生成的文件（`files.md`、`files.pptx`，都是 blob）；
  - 结构检查、读回核对、渲染检查的结果。
- 幻灯片是导出记录的上游（从 `slides` 派生 based_on）。幻灯片改版后，导出变成 stale：这时不能交付，渲染检查也拒绝（409，要重新导出）。
- 导出的文件、模板和 skill 的 blob 随记录一起进 git 留档（`blobRefsOf`，和来源的正文快照同一机制）；测试里用 `git cat-file` 核对过。
- `<项目>/exports/EX###/` 下放的是 blob 的副本（`deck.md`、`deck.pptx`）和渲染产物（`render-<时间>/`），不进 git；缺了就从 blob 再取。
- 渲染检查的结果写成导出记录的新版本，以前的结果留在历史里。

## 4. 导出方式

- **脚本**（`via: script`）：直接生成。
- **派给 Agent**（`via: 参与者 id`）：
  - 新建一个 `export` 任务，输入是全部幻灯片、`模板版式清单.json`（blob），有 skill 时再加 `skill-<文件名>`（blob）。内容版本都随任务包保存。
  - 派发时不给工具、输入内联（通用适配器也一样）。
  - 回复必须是 `{"slides":[{"id","layout","note"}]}`：每页正好一次、顺序和输入一致、版式名在清单里、有正文的页要有正文占位符。不合规时，这次尝试失败并写明原因，任务照常重试。
  - 合规时任务直接完成（`completeDirect`，方案记在任务结果上），服务收到“任务完成”事件后按方案生成。生成时用任务里记下的那份模板（从 blob 取），不读 `templates/` 里现在的文件。
  - 同一份方案不会重复生成。出方案之后幻灯片改过的，不能用这份方案（409）。生成失败时，页面上能“再生成一次”。
- **模板与 skill**：
  - `export.template`、`export.skill` 只认 `templates/pptx/`、`templates/skills/` 里的文件名，写路径一律拒绝。
  - 默认模板 `default.pptx`：16:9（960×540pt），主题字体西文用 Segoe UI、中文用微软雅黑，母版字号是标题 36、正文 24/20/18。
  - 自带一份 skill 示例 `简洁版式.md`。
  - 测试里换成 4:3 模板，读回的页宽从 960 变成 720，代码不用改。

## 5. 结构检查与读回核对

- **结构检查**（导出时做）。下面这些查出来都算问题：
  - 句子既没编号、也没标非事实；
  - 编号不在 claims 里；
  - 论断不存在、不是当前版本、或还不能进入成品（写明原因：核验状态、份数、阻塞异议、来源改版）；
  - 页面本身 stale 或有阻塞异议；
  - 正文字数超过 `slides.maxCharsPerPage`（不算编号、标记、空白）；
  - 讲者备注为空。

  claims 里有、正文却没引用的论断，只记为提示。
- **读回核对**（导出 PPTX 时做）：用 python-pptx 读回生成的文件，核对页数、每页的标题和正文（去掉空白后比较），备注不为空，备注里的标记（页序、版本、论断编号）对得上。

## 6. 渲染检查（实测）

- **自动化方式**：PowerShell 经 COM 调 PowerPoint 16.0。只读打开、不显示窗口，转成 PDF 和逐页 PNG（1600 像素宽），读出每个文本框的 `BoundLeft/Top/Width/Height` 和演示文稿的 `Fonts`。
- **对你自己开着的 PowerPoint 的影响**：只关自己打开的那份；PowerPoint 里还有别的演示文稿时不退出。
- **耗时**：一份 2–3 页的样本 15–40 秒，第一次慢一些（启动 PowerPoint、列字体）。
- **实测中修掉的坑**：
  - `pptx.py` 和 python-pptx 包同名：直接运行时它会遮住包本身，所以改名为 `pptx_export.py`，并且一律用 `python -I` 运行。
  - Windows PowerShell 5.1 按本机代码页读没有 BOM 的脚本，中文注释被读乱后解析失败，所以 `render.ps1` 存成带 BOM 的 UTF-8。
  - PowerShell 变量不分大小写：`$result` 和参数 `$Result` 是同一个变量，结果字典改名为 `$out`。
  - `[ordered]` 字典不能用属性语法加键，改用下标写法。
  - 控制台输出会把日文路径弄乱，结果一律写成 UTF-8 文件。
  - 默认模板第一版的占位符位置坏了：版式继承母版的位置，只改了左边距和宽度，写出的位置不完整，标题跑到了页面外。改成四个值一起写。这正好说明渲染检查有必要。
- **程序查的项目**：
  - **溢出**：排版范围超出文本框（容差 2pt）。
  - **超出页面**。
  - **重叠**：两个文本框的排版范围相交超过 4pt²。按实际排版范围判断，外框重叠、字没有叠在一起的不算。
  - **字体缺失**：用到的字体包括 PowerPoint 报告的、读回得到的和主题里的，逐个对照本机字体（WPF 的系统字体和当前用户安装的字体，各语言名称都算，所以“游ゴシック”和“Yu Gothic”都认得）。缺的字体按页列出；只在主题里用到的，列在整份上。
  - **图片变形**：显示宽高比和原图（扣除裁剪后）的宽高比差超过 2%。
  - **图表**：程序查不出标签有没有被裁切，只提示看图确认。
- **故意做坏的样例**（真 PowerPoint，测试与手动都跑过）：一个 4×1 英寸的文本框塞了 40 句话、用了不存在的字体 `NoSuchFont-WB`，再放一张 2:1 的图片拉成 1:1。查出 4 项：溢出（排版高度 864pt，框高 72pt）、超出页面、`NoSuchFont-WB` 缺失、图片变形。正常导出的样本 0 个问题。
- **没有 PowerPoint 时**：只查字体、图片和图表；溢出与重叠记为“未检查”，结论是 null，不给“通过”。
- **`render.engine: libreoffice`**：报错。本机没有安装 LibreOffice、无法实测，这一版没有接。
- **可交付**：结构检查、读回核对、渲染检查都通过，并且用到的幻灯片仍是当前版本。逐页视觉检查在 WP7b 加进来。

## 9. 已知限制，请重点看

1. **溢出的判断**：以文本框的尺寸为准。对“形状随文字调整大小”的文本框，文件里的尺寸要在 PowerPoint 里编辑后才会更新，所以只要文字超出原尺寸也算溢出。工坊生成的页面用的是版式占位符，不受影响；用户自己的模板如果有这种文本框，可能误报。
2. **字体检查**：PowerPoint 报告的字体里，会有主题按语言自动补上的字体（例如“游ゴシック”）。它们没安装时也会报出来。我认为这是对的：成品在这台机器上会用替换字体。
3. **字数**：去掉编号、标记和空白后，按字符计。英文单词按字母算，所以对中英混排比较粗。
4. **Agent 版式方案**：只决定每页用哪个版式，不改字号和配色（那些由模板管）。
5. **渲染进程超时**：超时（180 秒）会结束 PowerShell，但 PowerPoint 可能还开着那份文件（只读）。这种情况实测中没有遇到。
6. **可交付的条件**：WP7a 的“可交付”还不含逐页视觉检查，WP7b 补上之后才是验收用的条件。
