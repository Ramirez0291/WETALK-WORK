## 1. 接口依据

按 2026-10-18 的官方文档（api-docs.deepseek.com）实现：

- 对话：`POST /chat/completions`，模型 `deepseek-flash` / `deepseek-v4-pro`；`reasoning_effort` 取 none / low / high / max（none 即关闭思考）。
- usage 字段：`prompt_cache_hit_tokens`、`prompt_cache_miss_tokens`、`completion_tokens` 等。
- Search：`POST /v1/tools/search`，参数 `query` 1–128 字、`count` 1–50、`need_content`。结果字段有 `snippet`、`summary`、`content`、`authority`、`date`、`rerank_score`。
- Fetch：`POST /v1/tools/fetch`，参数 `url`，返回 `{title, content}`，content 是 Markdown。
- 错误：OpenAI 兼容格式。文档建议：408、429、5xx 重试；402 要充值；其他 4xx 改请求后再试。
- 计费与限速：Search、Fetch 各每 1000 次成功请求 $0.75，失败、空结果、超时不计费；每个账户每秒各 5 次。
- 价格：高峰价与低谷价（低谷为高峰的一半）；高峰为周一至周五 UTC 01–04、06–10 点。
- 文档**没有**承诺 `Retry-After` 头，所以有就用，没有就按配置退避。

## 3. 关键设计

### 3.1 重试、超时、中止

- 可重试：408、429、5xx、网络错误（连接被断开等）。不重试：其他 4xx（400、401、402、422……），错误信息取响应里的 `error.message`。
- 等待时间：`Retry-After`（秒数或 HTTP 日期）优先；没有就按 `retry.delaysSec`。重试次数为 `retry.max`。
- `timeoutMs` 是**整次调用的总时限**，包括所有重试和等待；超时或“停止”在请求进行中、等待重试时都立即生效（`abortableSleep`）。
- 失败的错误带 `details.attempts`（每次尝试的状态、耗时、等待时间）。429 重试用完后带 `rateLimited: true` 和 `retryAfterMs`，WP6 的冷却会用到。
- 非流式请求排队时，服务端先发空行保活，所以读完整个正文再 `trim` 后解析。
- `finish_reason` 为 `content_filter` / `insufficient_system_resource` / `aborted` 时按失败处理，并带上已消耗的 usage。

### 3.2 用量、费用与上限

- 每**一次尝试**（含失败和重试）先过 `beforeAttempt`（检查预算），结束后经 `onAttempt` 在 `<项目>/usage.jsonl` 记一行：api、ok、status、usd、usage、错误、元数据（query / url / source_id / purpose）。这满足“重试计入项目调用上限”。
- 费用：
  - 对话按“缓存命中输入 / 未命中输入 / 输出”分别计价，按调用时刻判断高峰或低谷。
  - 不认识的模型按已知最贵的价格估算，并标 `estimated`。
  - 不识别中国节假日（节假日官方算低谷），一律按高峰算，宁可高估。
  - Search / Fetch 只在成功且有结果时计费。
- 上限检查在发请求之前；费用要等返回才知道，所以最后一次调用可能略超费用上限（软上限）。调用次数是硬上限。
- 到上限后，新调用和重试都被拒绝（`AgentError('budget')`，HTTP 层 429），inbox 出现 `budget_exceeded`。重新加载账本（重启）后上限照样生效。
- 研讨室的讨论不属于任何项目，没有项目预算；用量照样写进调用记录。

### 3.3 Search 只给线索

- `/web/search` 的结果标为 `evidence: false`，并附说明。summary / snippet / content 都不会存成快照。
- `need_content: true` 拿到的 content 同样不是证据：只有 Fetch 的正文才能成为来源快照。

### 3.4 Fetch 与来源快照

- 正文存成 blob。给了 `source_id` 时，内容与当前快照相同就不升版；不同就以系统身份（`provenance.kind = 'system'`、`basis = 'web-fetch'`）经提交入口更新来源卡：新 `text_blob`、`retrieved_at`，来源升版 → 下游待复核。
- `create: true` 时新建来源卡；都不给就只存快照、返回 `text_blob`。
- 地址校验：http(s)、不超过 8192 字、不能带用户名密码。

### 3.5 来源可获取性（从来源卡里移出）

WP2 的来源卡里有 `availability` 字段。这次发现它和契约一冲突：Fetch 失败时如果改这个字段，来源就会升版，下游变成 stale、旧核验不再计入。而契约一要求“保留已有快照，快照仍可作证据”。所以改为：

- 来源卡里**不再有** `availability`（字段校验拒绝它），改加 `retrieved_at`。
- 可获取性从两份记录派生：主持人的确认（`availability.jsonl`，`gone` / `available`），以及最近一次带 `source_id` 的 Fetch 结果（usage 账本）。规则：
  - 主持人确认的 `gone` 优先，之后抓取成功也不改变，只能由主持人撤销；
  - 否则看最近一次抓取：成功为 available，失败为 temporarily_unavailable；
  - 从没抓过为 unknown。
- Fetch 失败：来源不升版，下游不变，快照照样能核对引文。失败记录（status、错误）留在账本里，作为契约一 `fetch_failure` 指针的依据。
- `gone` 自动生成“来源不存在”异议，按计划放在 WP5。

### 3.6 引文指针检查提前到晋升时（契约一第一步的 quote 部分）

WP3 的验收要求“搜索结果的 summary 或 snippet 不能作为引文进入论断”，这需要两件事同时成立：

1. **来源正文只有两个来处**：Fetch 快照（`text_blob`），或主持人手工录入（`text`）。非主持人身份提交 `text` 一律 403。
2. **晋升时检查引文**：论断每个带 `quote` 的来源引用，引文必须出现在**所引版本**的来源正文快照里。找不到为 `quote_not_found`；来源没有快照为 `quote_unverifiable`；两者都拒绝晋升。

这只证明“引文存在”，不证明“支持结论”。后者仍由核验者在 WP5 判断。

**实测发现**：真实 Fetch 返回的 Markdown 会给 ASCII 标点加反斜杠转义（例如 `permission\.`），并重排空白。照原网页抄下的忠实引文会因此匹配失败。所以 `locateQuote()` 两边都去掉 Markdown 标点转义、把连续空白压成一个空格，其余字符原样比较：全半角、中英文标点都不归一，标点不同就不算。追溯视图用同一函数定位，并显示快照里的原文片段。

## 5. 与文档的出入（待主持人同意后再改文档）

1. **来源卡移除 `availability`**，改为由抓取记录和主持人确认派生（理由见 3.5）。数据模型表里来源卡的字段要改。
2. **契约一 quote 指针检查提前到晋升时**，并定下引文定位规则：忽略 Markdown 标点转义与空白重排（3.6）。
3. **来源正文只能来自 Fetch 或主持人录入**（3.6）。
4. 新增配置 `deepseek.*` 与 `pricing.*`（只能全局设置）；`deepseek.timeoutSec` 是含重试的总时限。
5. 新增账本 `usage.jsonl`、`availability.jsonl`，不进 git。新增接口 `GET /usage`、`POST /sources/:id/availability`。
6. 费用上限是软上限（调用前检查，最后一次可能略超），调用次数是硬上限。

## 6. 已知局限

- 账本只在服务进程内累计；WP4 的任务调用接入后，项目预算才会真正覆盖 Agent 的对话调用（目前研讨室讨论不属于项目）。
- Fetch 的单域名限速没有公开数值，只能靠 429 重试。
- 引文定位不处理全半角、繁简、OCR 错字；要不要更宽松，留给 WP5 契约一一起定。
- 真实 Fetch 返回 example.com 时，正文开头是一段中文说明，后面才是英文原文。Fetch 的正文可能经过服务端处理，不一定与原网页逐字一致。目前把 Fetch 快照本身当作证据对象（与契约一“只认 Fetch 抓到的正文”一致），但要不要提醒核验者注意这一点，请你判断。
