## 0. 范围与主持人的决定

主持人这次定了四件事：

1. **WP6 一次做完**，不拆成两次评审。
2. **自动调度按项目开关，默认关**，另有“跑一轮”按钮。
3. **阶段用设计文档的七步流程，由主持人手动切换**。切换时由程序生成交接单（不调用模型），记忆空间换到新阶段。
4. **“一轮” = 一批派发到全部结束**。

## 1. 调度（scheduler.mjs）

- **开关**：项目的流程状态存在 `<项目>/workflow.json`，`auto` 默认是 false。
  - 打开时，规则循环持续推进：任务离开“进行中”时由事件触发，另有定时检查（`scheduler.intervalSeconds`，默认 30 秒）。
  - “跑一轮”（`POST /scheduler/run`）只派一次，不管开关。上一轮还没结束时返回 409。
- **开一轮**：从“可认领”的任务里，取依赖都已完成、不是导出任务的那些。按顺序挑参与者：
  - **指派了的**：只派给指派的那位。
  - **没指派的**：按分工表。任务类型到分工表工作类型的对应（`TYPE_ROUTE`）是我定的：
    - 收集来源 → search；抽取论断、补证 → extract；检查引用、核心结论、重要数字、对抗核验 → verify；
    - 选题角度、大纲、匿名评审 → outline；核心解释、因果解释 → key_writing；观众型读者 → summarize。
    - 分工表里的值按参与者 id 或适配器名匹配；`different_vendor` 指全部参与者逐个试，资格不够的（runner 返回 409，例如同厂商）换下一位。
  - **跳过的情况**（原因都写进 `last.skipped`，界面上能看到）：
    - 参与者不存在、不可用；
    - 冷却中；
    - 手上已有进行中的任务（`scheduler.maxPerParticipant`，默认 1；只数服务自己派发的，所有项目合计）；
    - `offPeak.defer` 打开时，高峰时段不派给 DeepSeek。
  - **一个都没派出去**：不开轮，只记原因。
- **上限**：认领时超出调用次数或费用上限，任务按契约三转“待你决定”（这是 tasks.mjs 原有的规则）。调度看到 429 就停止这个项目这一轮的派发，“待你决定”里加一条 `scheduler_budget`。
- **争议分流**：补证任务照旧由规则（evidence.mjs）生成，调度按分工表派发；核验结论不一致、补证用完的照旧进“待你决定”。调度不会自己为论断新建核验任务（见第 8 节）。
- **只做派发**：揭晓、选定、裁决这些决定，调度一概不做。

## 2. 冷却

- **怎么判断**：runner 新增回调 `onFailure`，调用失败时把原始错误交给调度。
  - API 报 429（DeepSeek 客户端的 `details.rateLimited`）：按 `retryAfterMs` 冷却，没有就按 `cooldown.apiSeconds`。
  - 命令行 Agent 报错里有额度用完或限流的字样（usage limit、rate limit、quota、429、too many requests、overloaded、额度、限流）：冷却 `cooldown.cliMinutes`。
  - 判断只在内存里做，报错原文不落盘。密封任务的报错照旧按契约四清理。
- **怎么记**：冷却按参与者记，所有项目共用，存在 `projects/_cooldowns.json`，重启后仍在。
- **只管自动派发**：冷却期间调度不派给这位参与者；你手动派发不受限制，由你自己决定。

## 3. 轮与停滞（changelog.mjs）

- **收轮**：这一轮派出的任务都不在进行中了，就收轮。“进行中”指已认领，或已交稿等晋升。
  - 密封任务交稿后等你揭晓，不算进行中；尝试失败回到“可认领”的，也不算，下一轮再派。
- **快照**：开轮前和收轮时各取一次，比对：
  - **内容**：每条正式记录去掉版本号和内容生产者字段后的正文 hash。只换了版本号、正文没变的新版本，不算变化。
  - **质量指标**：
    - 支持且份数够的论断（`id@version`）：看有没有新增；
    - 有阻塞的异议：看有没有解除；
    - 最近一次揭晓了的观众型读者标出的不懂处数量：看有没有变少。
- **结论（`assessRound`）**：三种情况分开记录。
  - **没填改动记录**：写了记录的任务没交改动记录，单独记（`changelog.not_filled` 和任务清单），不算停滞。
  - **内容没有变化**（unchanged）：算停滞。
  - **有变化但质量指标没有提升**（no_improvement）：算停滞。
  - 另外两种不算停滞：**没有任务完成**（no_result），以及**只有读者或评审、内容没变**（reading）。
  - Agent 自报的改动类型（evidence / fix / clarity）计数记在 `self_reported`，只作辅助，不影响结论。
- **连续停滞**：连续 `plateau.rounds` 轮停滞，按 `plateau.action` 处理。
  - **audience_reader**：新建观众型读者任务，读当前作品（有幻灯片读幻灯片，否则讲稿，再否则大纲），下一轮派发。上一份调度建的新读者任务还没结束时，不再加。
  - **needs_user**：交给你决定，“待你决定”里加一条 `stagnation`。没有作品可读时，也走这条。
  - 处理完，连续停滞计数归零。
- **改动记录**：
  - **格式**：读资料任务的输出可以是 `{"changes":[…],"changelog":[{"id":"C003","type":"fix","note":"…"}]}`，原来的纯数组照样接受。新建的记录在那条改动里写 `tmp`，改动记录写这个临时编号。
  - **落盘**：晋升成功后，临时编号换成正式编号，只留这次真正写了的记录，写进 `<项目>/changelog.jsonl`。指向没写的记录、类型不对的，记为 invalid。
  - **提示词**：读资料任务的提示词已加上这段说明。
- **观众型读者的输出**：改为 JSON（`restatement`、`confusions`），这样不懂处才数得出来。没有 JSON 时，数“看不懂”那一段之后的列表项。

## 4. 阶段（phases.mjs）

- **七步**：明确目标、收集来源、抽取论断、大纲、讲稿、幻灯片、审阅。
  - 由你在“调度”页切换（`POST /phase`），可以跳着切，也可以往回切。
  - 一轮还没收轮时，切换返回 409。
- **切换时依次做**：
  1. 程序从正式记录、派生状态、竞争和最近几轮的记录生成交接单（`buildHandoff`），不调用模型：
     - 现状：来源与论断各类计数、待更新数、作品清单；
     - 没解决的事：阻塞异议、有分歧的论断、待你决定的条数、竞争的选定结果；
     - 最近几轮的结论，以及给下一阶段的说明。
     - 不写内容生产者的身份（参与者、模型、厂商，主持人也不写）；超过一页（2500 字）就截断，每组最多列 8 条。
  2. 旧阶段的工作记忆按契约四先归档、再清空（`resetPhase`）。归档失败时报错，阶段不切换。
  3. 交接单写成 `<项目>/handoff/H###.md`。
  4. 新阶段的记忆空间“工坊·项目名·阶段名”建好；`workflow.json` 记下这次切换（谁、何时、归档了几份工作笔记、归档文件）。
- **任务包**：新阶段的读资料任务和密封起草任务，任务包带上当前阶段的交接单（作为输入，存档可还原），不带此前的讨论。
  - 观众型读者不带，因为交接单里有论断计数；匿名评审也不带。
- **研讨**：挂到项目上的议题，记忆默认用当前阶段的空间；还没设阶段时，沿用 WP5b 的“研讨”空间。

## 8. 已知限制与请你重点看的地方

1. **按文档的质量指标，收集期的轮会被判停滞**：
   - 原因：文档列的指标是新增 supported 论断、解除阻塞、不懂处变少。只新增来源和论断、还没核验的一轮，结论是“有变化但没提升”。默认 `plateau.rounds` 为 1，这时收集来源、抽取论断阶段的轮会触发新读者；没有作品时会进“待你决定”。
   - 我照文档字面实现了。可以考虑的改法：把“新增来源或论断”也算一项指标，或者只在大纲及以后的阶段判停滞。请你和主持人判断。
2. **分工表的对应是我定的**：任务类型到分工表工作类型的对应（第 1 节），文档没写，请看是否合理。
   - 另外，本机的真实配置里没有 DeepSeek 参与者，所以默认分工表里 extract、search、summarize 的任务不会自动派，界面上会写明原因。
3. **命令行 Agent 的额度判断靠报错字样**，是启发式：漏判时不会冷却，误判时会多冷却一段。
4. **你手动派发不看冷却**：冷却只约束自动派发。
5. **自动调度只派已有任务**：不会为论断自动新建核验任务，也不会为待更新的下游自动建复核任务（设计文档提到“上游更正会变成新的待复核任务”）。我认为这超出了文档 WP6 的条目，留作以后的规则。
6. **轮按批算，不按单件作品算**：同一轮里有的作品有进展、有的停滞，只看整轮。
7. **交接单只取事实，不写摘要**：没有模型写的要点，所以讨论里的结论不会出现在交接单里（讨论截断时另有“决议摘要”）。
8. **不进 git**：workflow、交接单、改动记录、冷却都和任务一样由服务维护。
9. **定时检查的间隔取全局设置**：项目里改 `scheduler.intervalSeconds` 不起作用，因为只有一个全局循环。
10. **`scheduler_budget` 不会马上消失**：这条提示一直留到下一次派发。
