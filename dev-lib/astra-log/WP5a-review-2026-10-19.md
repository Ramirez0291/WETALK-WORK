## R1 · P1 · 人工小改会洗掉作者约束，使原作者的自核验计入独立份数

位置：`lib/workbench/verify.mjs:65`、`116`，以及派发检查 `lib/workbench/runner.mjs:107`。根因关联 `lib/workbench/commit.mjs:352` 的版本 provenance 覆盖。

复现（`original-author-after-human-edit`）：

1. DeepSeek 写 C001 v1，正文为 `Population is 1200`，引用 S001。
2. 主持人仅补一个句号，保存为 v2，来源和论断含义不变。
3. 同一个 DeepSeek 参与者提交对 v2 的 supported 核验。

实际：当前 provenance 只记 human；核验以 human 对 deepseek 判为跨厂商，`independent: 1`、`enough: true`、`ready: true`。这使原内容作者核验自己的论断成为“独立核验”。历史里虽然还能查到旧版作者，但资格检查没有使用该来源关系。

开发文档明确要求“人工编辑和移植补丁保留原内容的来源关系”。此问题在开发日志第 8.6 节已被指出，但未列为主持人批准的契约例外。原先版本 provenance 的实现，在 WP5a 新增独立性判断后产生了直接的错误放行，不能仅作为显示层限制保留。

建议：区分本次编辑者与内容来源，保留可追溯的作者关系；晋升检查、核验计数、对抗核验派发及异议裁定使用同一作者关系规则。无需把任何后续实质改写永久归给第一位作者，但人工小改不能自动抹掉原作者的排除条件。

补测：Agent 起草 → 主持人标点/格式小改 → 原 Agent 或同厂商 Agent 核验仍不能计入；其他厂商的合法核验可以计入。主持人新创作的独立论断仍按 human 作者规则处理。

## R2 · P1 · 厂商不明的 Agent 可以裁定并解除阻塞

位置：`lib/workbench/objections.mjs:124–125`。

judge 分支仅拒绝“作者厂商已知且与裁定者相同”，没有要求非主持人的裁定者与作者厂商均可确定。因此厂商 unknown 会被当成不同厂商；作者 unknown 时也直接跳过比较。

复现（`unknown-vendor-judge`）：DeepSeek 写论断，Claude 提 open 的数字异议；再由服务端认领任务的 generic Agent（没有可推断厂商的模型）提交 rejected。实际晋升成功，异议为 rejected，`blockers: []`，裁定者 provenance 明确为 `vendor: unknown`。

“身份已证实”只能证明服务调用了这个参与者，并不证明它与作者跨厂商。相同配置在核验计数与 verify_claim 派发中会被排除，却能在此永久取消事实性阻塞，违反契约一的裁定者约束。

建议：对非主持人的 judge 同时要求作者、裁定者厂商可确定且不同；未知时保留异议或转 needs_user，不允许直接 upheld/rejected。保留主持人已批准的厂商例外，以及提出者/作者不能自裁的限制。

补测：裁定者 unknown、作者 unknown、双方 unknown 均不能由非主持人裁定；正常跨厂商和合格主持人路径仍通过。

## R3 · P2 · 已报告的实际厂商与配置冲突时，仍按配置计入核验

位置：`lib/workbench/runner.mjs:194`；身份从 `144` 的配置 holder 经任务栅栏进入提交，没有按本次调用报告复核。

复现（`reported-vendor-mismatch`）：作者是 Codex/openai；派发给配置为 claude 的假 Agent，返回结果的 `model` 为 `gpt-6-fixture`。调用日志明确写入 `reported.vendor: openai`，但 V001.verifier 仍为 anthropic，任务 done，论断 `ready: true`。

触发条件是参与者配置与本次适配器报告不一致，例如路由、模型回退或配置错误。这里不要求相信任意用户自报身份，也不要求在缺少模型报告时猜测；问题在于系统已经收到明确的冲突信息，却继续断言跨厂商成立。开发日志第 8.1 节已说明这一限制，但它不符合身份按本次尝试与调用记录派生的契约，也未在本轮批准的文档修订中豁免。

建议：把服务端采集的本次模型/厂商报告关联到该 attempt 的身份检查；至少在已知配置与报告冲突时拒绝计数或标为待确认，不能继续按配置放行。作者侧和核验者侧需要采用一致的身份依据。

补测：报告厂商与作者相同、与配置冲突；报告正常一致；没有报告。分别验证 provenance、计数和派发/晋升结果。

## R4 · P2 · 论断改版后，补证任务读取新版而不是异议所指的版本

位置：`lib/workbench/evidence.mjs:38–43`。

规则用 `records.get(o.target.id)` 取当前目标，并把当前版本放进任务 inputs。异议的 target 却不可变，仍指向原版。`collectInputs` 随后按任务中这个错误版本附上来源正文。

复现（`evidence-target-version`）：O001 待补证，target 是 C001@1，原版引用 S001；C001 升到 v2 后改引 S002；此时规则生成的补证任务 inputs 是 O001@1、C001@2，正文仅含 S002@1，遗漏仍然存在的 S001@1。

结果：Agent 被要求为旧版异议补证，却看不到旧论断和旧来源。该任务没有工具、只能根据内联材料判断，可能白白耗完补证名额，或给旧版异议附上新版的证据。

建议：任务固定引用 `o.target` 的版本，利用现有按版本读取/归档机制收集正文。若同时提供新版用于比较，要显式区分，不能替换被挑战的原版。来源、作品目标也应遵守同一原则。

补测：提出 needs_evidence → 修改目标及其来源 → 生成/重试补证；任务包必须能还原被挑战版本及其对应正文。

## R5 · P2 · gone 异议进入 needs_user 后，撤销 gone 的自动撤回必定被拒

位置：`lib/workbench/evidence.mjs:75–81`，与 `lib/workbench/objections.mjs` 的 needs_user 仅主持人转换规则冲突。

复现（`gone-undo-needs-user`）：

1. 主持人确认 S001 gone，规则生成 O001 open。
2. 已证实的参与者因争议把 O001 转 needs_user。
3. 主持人撤销 gone，来源已恢复 available；规则尝试 withdrawn。

实际：规则以 system 身份晋升，返回 409，原因 `role / need: host`；O001 保持 needs_user，继续阻塞。一次 reconcile 在这里抛出，也会中止后续自动撤回处理。

开发文档对 gone 的特殊约定是：撤回规则自己提出、尚未结束且未被裁定成立的异议，包含这一状态。通用状态机又规定 needs_user 仅主持人处理，两者尚未在实现上衔接。

建议：实现严格限定的 gone 撤销规则例外，或把该自动动作绑定到主持人的这次撤销授权。不要为了修复而允许任意 system 修改所有 needs_user 异议；upheld 仍须保留。

补测：gone 异议分别为 open、needs_user、upheld 时撤销确认；前两者按契约撤回，upheld 保留；多条异议不会因其中一条而漏处理。

## R6 · P2 · 编号超过三位后，“最新核验”会取回旧判断

位置：`lib/workbench/verify.mjs:60`。

按 id 的 `localeCompare` 排序后覆盖 Map 来选“最新一份”，但编号只补齐到至少三位，支持继续增长到六位。字典序中 V1000 排在 V999 前面。

复现（`latest-verification-after-999`，纯函数夹具，未创建千条磁盘记录）：同一核验者先在 V999 判 supported，后在 V1000 改判 unsupported。实际返回 supported、counted=[V999]、enough=true，反而把 V1000 标为 superseded。

这会在项目累积核验超过 999 条时忽略较新的反对判断，并错误维持可进入成品。

建议：按数值序号或明确的已提交顺序取最新，不按普通字符串排序；不要仅扩大固定补零宽度掩盖边界。

补测：V999/V1000、V9999/V10000，以及相反的改判方向。

## R7 · P2 · 异议 resolve 接口的相同 request_id 重试被误判为内容不同

位置：`lib/workbench/http.mjs:260–264`。

该接口每次调用都会重新读取异议当前版本，再构造 expected_version。第一次成功使 O001 从 v1 变成 v2；客户端若没收到响应，原样重试同一个 request_id，请求体虽然完全不变，服务端生成的 changes 却变成 expected_version=2。

复现（`resolve-request-id-retry`，直接调用真实路由 handler）：第一次以 `repeat-resolve-0001` 把异议改为 rejected 成功；完全相同的请求重试返回 409：`request_id repeat-resolve-0001 已用于内容不同的提交`。

结果：已经成功的操作被报告为冲突，不能履行提交入口“响应丢失后用同一 request_id 返回首次结果”的约定。这不是要求再次执行终态转换，而是要求返回已完成操作的结果。

建议：先依据原始操作与 request_id 复用首次构造的提交/结果，或让客户端显式提供固定 expected_version 并纳入稳定请求；保证真正不同的内容仍冲突。

补测：首次成功后同请求原样重试，返回相同 sid/cid、不产生第二版；同 request_id 换 state/resolution 仍返回冲突。
