## 2. 关键设计

### 2.1 记录与编号

- 种类与前缀：来源 `S`、论断 `C`、核验 `V`、异议 `O`、大纲 `OL`、讲稿 `SC`、幻灯片 `SL`，编号 3–6 位数字。开发文档只规定了 S/C/V/O/T，作品的前缀是我定的。
- 记录文件 = 业务字段 ＋ 系统字段：`id`、`version`、`provenance`、`commit`、`updated_at`。系统字段由提交入口填写，提交内容里出现就拒绝；`based_on` 和所有状态不写进文件。
- 引用一律 `{id, version}`，缺版本号就拒绝。同一次提交里新建的记录可以用临时编号互相引用（`tmp: "$s1"`，引用写 `{"id":"$s1"}`），晋升时换成真实编号。
- 字段校验只允许论断引用来源、作品引用论断，引用关系在结构上分层，写不出环。`derive()` 仍做环检测，防伪造文件。
- 来源正文：提交时给 `text`，收稿时存成 blob，记录里只留 `text_blob`。
- **核验记录和异议暂不接受写入**（返回“WP5 实现”）。它们的写入规则（跨厂商、人类核验计数、异议状态机）属于契约一；在没有这些规则之前开放写入，就可能写进同厂商核验。`deps.mjs` 已经按文档读取它们，测试直接构造记录集合。

### 2.2 内容来源（provenance）

按你在 WP1 评审里的意见实现：

- 身份只由服务端给出。HTTP 层不读请求体里的 author / kind；没有任务号的提交必须带 `X-Workbench-Host` 令牌，才记为 `{kind: 'human', participant, verified: true, basis: 'host-session'}`。
- 令牌每次启动重新生成，只注入 `/workbench` 页面。**局限**：它只证明请求来自加载过工坊页面的客户端，防不住刻意抓取页面的本机进程。本机进程隔离属于契约四的范围，WP2 不宣称完成。
- 带任务号的提交走 `fence.check()`。WP4 之前它一律返回“任务不存在”（404），所以 WP2 只有主持人入口能写。
- provenance 按版本写进记录，带 task / attempt / sid。

### 2.3 收稿

- 同步完成：同一 `request_id` 的并发重试不会各自存一份。内容 hash 对 `{task_id, attempt, changes}` 做键排序后计算；相同返回第一次的回执（`duplicate: true`），不同返回 409。幂等索引在重启后从候选稿重建。
- 候选稿目录 `candidates/<sid>/submission.json`。sid 为 `<任务>-<尝试>-<时间>-<随机>`，主持人提交为 `H-<时间>-<随机>`。文档写的是 `candidates/<任务>-<尝试>/`，但同一尝试可能有迟到的历史草稿，所以加了后缀。
- 栅栏不通过的提交存为 `fenced: true` 的历史草稿，永不晋升（WP4 才会出现）。

### 2.4 晋升（临界区内依次检查）

1. 目标记录存在，当前版本等于 `expected_version`；
2. 目标文件的 hash 等于最后一次 applied 记录的 blob，否则判为外部改动，拒绝覆盖；
3. 分配新编号：跳过目录里所有已存在的文件名，坏文件也算，绝不覆盖；
4. 每个引用都等于提交之后的当前版本（引用同一次提交里修改的记录时，按修改后的版本算）；
5. 无环。

任一项不满足：候选稿保留，在 `attempts.jsonl` 记原因，返回 409 和 `details.reasons`。全部通过才分配提交编号。

### 2.5 写前日志（契约二的 1–5 步）

1. 新内容和旧内容都先存成 blob；再写 `_txn/<cid>/manifest.json`（临时文件 ＋ 改名）。
2. 旧版本从 blob 复制到 `archive/versions/<目录>/<id>.v<n>.json`。
3. 逐个文件：临时文件 ＋ `renameRetry`。
4. 追加 `commits.jsonl` 的 applied 行（成功标志），记审计事件，删掉 `_txn/<cid>`。
5. `later(archive)`：接口先返回，留档仍占着队列，不会和下一次晋升交错。

**恢复**（启动时，持有锁之后）：

- 修掉 `commits.jsonl` 末尾的半行；
- 删除残留的 `_staging-*`；
- 没有清单文件的 `_txn` 目录直接丢弃；有清单、没有 applied 的，按清单重做 2–4 步（每步可重复执行）；已 applied 的删目录；
- 未留档或留档失败的重新排队。

**外部改动**：每次查询 inbox 时实时比对，不持久化。没有任何 applied 记录的记录文件、提交过但被删掉的文件，也都算外部改动。

### 2.6 git 留档

WP1 用 `git add` ＋ `git commit -- <paths>` 提交工作区文件。这样做有两个问题：一是留档时工作区可能已经被下一次晋升改写；二是 attributes 或过滤器可能改动内容（你在评审里指出的）。WP2 的留档改为 `commitBlobs()`：

- 在临时索引上：`read-tree HEAD` → 对每个文件 `hash-object -w --no-filters <blob 文件>` → `update-index --cacheinfo` → `write-tree` → `commit-tree` → `update-ref HEAD <new> <old>`（带旧值，HEAD 被别人移动过就失败）。
- 不碰工作区，也不碰用户已暂存的其他改动。最后对本次路径做 `git reset -q --`，让用户的索引跟上新的 HEAD。
- 严格按提交编号顺序留档：前面失败，后面等着，避免旧内容覆盖新内容。失败行只在错误信息变化时追加，避免每分钟一行。
- 项目的 `git.autoCommit = false` 时记 `archive_skipped`。
- 新建项目仍用 WP1 的字面路径 `add/commit`（模板文件没有 blob），但已经进了同一个队列。

projects 仓库的 `.gitignore`（`init()` 会补齐缺的行并提交）：锁、`*.tmp`、`_staging-*`、`_txn/`、`commits.jsonl`、`*/events.jsonl`、`*/candidates/`、`*/archive/versions/`、`*/archive/blobs/`（正文快照 blob 经 `commitBlobs` 照样被跟踪）。理由：git 只留正式记录的历史，不参与恢复，这和契约二“谁是事实来源”一致。

### 2.7 单实例锁

- `projects/.workbench.lock`（`wx` 创建）。持有者进程活着就拒绝（423）；进程已不存在，说明上次异常退出，锁作废。
- 锁文件刚建出来、还没写完（5 秒内读不出 JSON）时视为有人持有。
- `stop()` 只删自己 token 的锁。Windows 上进程被强杀时不会执行 exit 钩子，下次启动按“进程不存在”作废。PID 复用的极端情况没有处理。
- 服务启动顺序：取锁 → `workbench.init()`（git init、补 `.gitignore`）→ 恢复。WP1 是在锁之前 init，已改。

## 5. 已知局限与留给后续

- 外部改动只能发现、拒绝覆盖，还没有“采纳为新版本 / 从 blob 还原”的处理入口（WP4 做 inbox 时加）。
- 引文检查是精确子串匹配，空白和全半角不归一。契约一（WP5）再定规则。
- 每次查询和晋升都从磁盘全量读取记录。试运行规模（几十到几百条）没问题，以后需要时再加缓存。
- 主持人令牌的局限见 2.2。
- 工坊页面目前只有中文，没有接入 WeTalk 的 i18n。
- `project.md`、`protocol.json`、`baseline.md` 由主持人直接编辑，不经提交入口，也不做外部改动检测；它们的留档目前靠手工或新建项目时的提交。
