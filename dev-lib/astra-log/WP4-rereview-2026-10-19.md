## R1 · P1 · 密封调用失败的正文仍写进用量账本，并可经 HTTP 读取

位置：`lib/workbench/runner.mjs:213`。出口：`lib/workbench/http.mjs:108–109`。

当前 catch 在生成经过清理的 `call.error` 之前，先调用 `usage.settle(..., { error: e.message })`。CLI 适配器的失败消息会附带 stdout/stderr 尾部，因此原始部分草稿仍进入 `usage.jsonl`。随后 `GET /api/projects/:p/usage` 把 `usage.entries()` 最近 50 条直接返回，接口层也没有去掉 error 内容。

这不是上轮问题已经全部解决后新增的独立要求：契约四要求密封期间任何文件和 HTTP 中都不能有未揭晓的正文。上轮修复只清理了 `calls.jsonl` 与任务历史，遗漏了同一错误的第三个持久出口。

复现使用真实 generic 适配器执行一个本机假 Agent：读取 stdin，输出 `SEALED-USAGE-CANARY-1931`，以退出码 1 结束。没有调用真实模型，也没有把金丝雀放进命令行参数。

观察：

| 检查点 | 含金丝雀 |
| --- | --- |
| calls.jsonl | 否 |
| 任务 JSON / 历史 | 否 |
| usage.jsonl | **是** |
| 用量接口所用的 recent 条目 | **是** |

修复建议：在错误进入任何持久账本前，统一按可见性生成安全错误信息；CLI 结算、API hooks、调用日志及任务历史都应遵守同一规则。不要仅在 HTTP 输出时隐藏，因为磁盘本身也属于验收范围。API 错误还需核对 `exec.attempts` 等嵌套字段，避免其他响应原文绕过清理。

补测：密封任务输出一段正文后失败，在整个项目目录、调用目录、用量接口与任务接口中扫描金丝雀；除了调用日志和任务历史，必须覆盖 usage.jsonl。成功且含工具审计参数的稿件继续验证揭晓前不落盘、揭晓后才补写。

## R2 · P1 · 揭晓在完成前就删除轮次，取消或写盘失败会丢失其他结果

位置：`lib/workbench/visibility.mjs:157–161`；调用顺序：`lib/workbench/runner.mjs:253–262`。

`sealed.reveal()` 检查数量后立即 `rounds.delete()`，runner 才逐项写正文 blob、补调用记录、执行 `board.completeSealed()`。后续任何一步抛错，都没有恢复轮次。揭晓前也未检查所有任务是否仍为本轮的 submitted 尝试。

**复现 A：正常取消路径。** 同一轮包含 T001、T002，两者都已收集到内存、处于 submitted；主持人取消 T001，再揭晓。

- 首次揭晓返回 409：T001 已 cancelled，不能完成揭晓。
- T001 的正文已经先写进 blob 和调用日志；T002 的正文还没有写出。
- 轮次已经不存在，再次揭晓返回 404。
- T002 仍为 submitted，但其内存结果已丢失，无法正常揭晓或重新认领。

**复现 B：可恢复的写盘错误。** 单任务已收集后，在该临时项目的 blob 写入处注入一次 ENOSPC。首次揭晓抛 ENOSPC，恢复文件操作后再试却返回 404；任务仍为 submitted、轮次为 null。这里服务没有崩溃，因此“进程崩溃后本轮重跑”的约定不能解释这种状态。

修复建议：将“查看/校验结果”与“确认揭晓完成并释放内存”分开。先验证所有成员的项目、任务、尝试与可揭晓状态，再执行可重试的写盘流程；全部成功后才移除轮次。明确已取消成员的处理规则（移出或取消整轮等），保证其他成员可继续完成或明确重开。多项写入中途失败时，应保留未写出的结果，且重复揭晓不得重复完成任务或追加重复 fill_of。不能只捕获异常并返回成功。

补测：

- 两份稿都完成后取消其中一份，再揭晓；其他稿不会丢失或永久停留在 submitted。
- 第一份成功、第二份 blob / 调用日志 / 任务文件写入失败，修复故障后同轮次可继续完成。
- 重复揭晓不重复写调用补充记录、不改变已完成结果。
- 校验失败发生在任何正文发布之前；迟到尝试不能借揭晓重新进入结果。

## 回应开发日志中的设计问题

**输入内联、关闭工具：** 接受当前经主持人批准的取舍。实测已说明临时 cwd 不能充当隔离，改为显式输入可降低上下文越界风险。长来源应按任务选取可追溯的片段或拆分任务，保留原版本、定位和实际发送内容；不应为了缩短提示词而静默截断引用依据。通用适配器的工作目录隔离仍仅是约定，不能把它等同于操作系统隔离。

**栅栏与身份：** 按凭证关联任务尝试，外部 MCP 自报身份保持未证实，过期尝试不借用当前持有者身份，这些方向正确。收稿、晋升和密封收集均需要各自检查生命周期；本轮 R2 说明揭晓也是生命周期的一部分。CLI 配置模型与实际报告模型仍应区分，后续 WP5 的厂商独立性判断不能只凭显示名称或自报身份。

**密封结果只在内存：** 按批准的“揭晓前崩溃则重跑”语义可以采用；但无正文的占位必须覆盖所有持久出口，包括用量账本、错误嵌套字段与任务状态。揭晓前的重跑约定也不免除揭晓过程的失败恢复要求。当前不能宣称“任何磁盘文件与接口都拿不到密封稿”。
