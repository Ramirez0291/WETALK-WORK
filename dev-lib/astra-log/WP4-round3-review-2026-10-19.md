## R1 · P2 · 调用日志部分写入后重试揭晓，会返回成功但损坏审计记录

位置：`lib/workbench/runner.mjs:307–310`；底层原因：`lib/calllog.mjs:55–60`。

触发：密封稿已收集，揭晓向 `calls.jsonl` 追加 `fill_of` 记录时，部分字节已写入，随后发生 ENOSPC。释放空间后，在同一服务进程中重试揭晓。

`createCallLog.append()` 仅在 `appendFileSync` 完全成功后更新内存索引和 size。部分追加后抛错时，文件保留半行，而索引与 size 仍指向追加前的边界。runner 的 `log.list(...fill_of...)` 查不到本次补充记录，于是把完整 JSON 直接追加到半行后面；同时索引仍用旧 offset。随后任务转 done、轮次被清除，接口返回揭晓成功。

结果：该行不是有效 JSON，当前进程 `getMany()` 读取补充记录抛 SyntaxError；重新打开日志后，解析器跳过坏行，揭晓补充记录消失。**正文 blob 和任务结果仍在，此处不是草稿整体丢失；受损的是揭晓的调用正文与审计补充记录，以及日志可读性。**

附加探针只对临时项目的目标 calls.jsonl 注入一次故障：先实际追加本条记录一半的字节，再抛 ENOSPC，然后恢复正常文件操作并重试。实际输出：

```json
{
  "firstError": "ENOSPC",
  "retriedResults": 1,
  "taskState": "done",
  "round": null,
  "inMemoryFillCount": 1,
  "fillReadError": "SyntaxError",
  "invalidJsonLines": 1,
  "fillCountAfterReopen": 0
}
```

现有新增测试覆盖的是在调用日志写入之前直接抛错，没有覆盖部分字节已落盘。底层 append 工具早已存在，但 WP4 本次揭晓重试依赖它的成功/失败语义，因此该问题直接影响本次修复所承诺的可恢复揭晓。

修复建议：使追加失败后的文件边界、索引和 size 保持一致；在单写入者约束下，可将不完整追加回滚到已确认边界，或先修复尾部并重建索引，再允许重试。还需明确完整记录已经落盘但调用报告失败时的幂等处理，确保每个 callId 最终只有一条有效 fill_of。仅补一个换行不能修复已失真的 offset，也不能恢复被截断的记录。无法恢复时应继续报错并保留轮次，不应完成任务并释放唯一内存审计数据。

补测要求：真实写入部分字节后抛 ENOSPC，恢复后重试；随后逐行解析文件、通过当前 log 读取、重新创建 log 读取，三者都应成功，且每个 callId 恰好一条有效补充记录。多成员轮次的已完成成员仍不重复补写。
