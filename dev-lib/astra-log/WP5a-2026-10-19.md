## 0. 范围与主持人的决定

主持人同意把 WP5 拆成两次评审：

- **5a（本次）**：契约一（核验、异议、补证、来源 gone 时自动异议），以及对抗核验。
- **5b**：分工、竞争（密封起草 → 匿名评审 → 选定 → 移植补丁 → 书记），以及工坊与研讨室的整合。

主持人另外定了三件事：

1. **“独立核验”按核验者去重**：不同参与者各算一份，同厂商的两个参与者也各算一份；主持人算一份。
2. **竞争方案先由主持人选**，研讨室的表决以后再接（5b）。
3. **异议新增 `resolved` 状态**：成立的异议，在论断改版并重新核验通过后可以关闭（文档修订，见第 6 节）。

## 1. 记录与写入（records.mjs、commit.mjs）

核验记录（V）和异议（O）现在可以经提交入口写入。

- **核验记录**：`target`（论断 id@version）、`source_versions`、`verdict`（supported / unsupported）、`reason`；判 supported 时还要 `support_quote`（`{id, version, quote, locator?}`）。
- **异议**：`target`（论断、来源或作品的 id@version）、`category`（三类阻塞 ＋ interpretation / narrative / extension）、`pointer`、`reason`、`state`、`resolution`。
  - 指针有五种：`quote`（来源原文）、`fetch_failure`（带用量账本里那次抓取的记录号）、`missing_source`、`gone`（只限规则）、`location`（只是文字描述）。
- **由提交入口填写的字段**：核验记录的 `verifier`、异议的 `raised_by`，按服务端认定的身份（`provenance`）填写，提交内容里出现就拒绝。异议的新版本沿用最初的 `raised_by`。
- **不能用临时编号**：两者的 target 都不能是本次提交里新建的记录（`$`）。核验者与作者不能是同一次提交。
- **核验记录只增不改**：改主意就另写一份；同一核验者只算最新的一份。

写入规则在晋升时、仓库队列的临界区里检查（新增“3b”步）。用的是晋升前的正式状态，所以“改论断的同时核验它”会因为目标版本不对而被拒。

## 2. 核验（verify.mjs、deps.mjs）

**写入检查**（`checkVerification`）：

- target 是论断的当前版本；
- `source_versions` 正好是论断所引的每个来源的当前版本；
- 判 supported 时，支持引文出自论断所引的来源，并能在那个版本的正文快照里定位（沿用 `locateQuote`）；
- 核验者与作者同厂商：拒绝。这包括同厂商的另一个模型、自报同厂商的 MCP 会话，以及主持人核验主持人自己录入的论断（human 对 human）。

**份数**（`countVerifications`，deps.mjs 调用）：

- 只看绑定“当前论断版本 ＋ 每个来源的当前版本”的记录。
- 按核验者（主体类型＋参与者）去重，取最新一份。
- 下面几种保存但不计入，详情里列出原因：身份未证实（MCP 外部会话）、推断不出核验者的厂商、推断不出作者的厂商（核验者是主持人时除外）。
- 派生结果新增 `independent`（支持的独立核验者数）、`required`（核心结论 `verify.coreClaimVerifiers`，其他 `otherClaimVerifiers`）、`enough`、`uncounted`。
- “可进入成品”从“supported”改为“supported 且 `enough`”，另外仍要求 current、无阻塞。核验状态的四个取值不变。

## 3. 异议（objections.mjs）

状态机（`checkObjection`）：

| 从 | 到 | 谁可以 |
| --- | --- | --- |
| （新建） | open / needs_evidence | 任何人；只能针对目标的当前版本；needs_evidence 只用于三类阻塞异议 |
| open | upheld / rejected | 裁定者：身份已证实（服务派发的任务或主持人）；不是提出者，也不是作者；与作者不同厂商（主持人除外）；必须写理由 |
| open | needs_user | 身份已证实的任何一方，写理由 |
| open、needs_evidence | withdrawn | 提出者（或主持人） |
| needs_evidence | open | 身份已证实的任何一方，同时补上有效指针 |
| needs_evidence | needs_user | 规则（补证次数用完）或主持人 |
| upheld | resolved | 身份已证实的任何一方；要求目标已改版，且新版本当前、核验份数够（作品与来源只要求已改版且当前） |
| needs_user | 任一状态 | 只限主持人 |

- rejected、withdrawn、resolved 是终态。被驳回的提出者可以附新证据另提一条。
- target、category 一经提出不能改；指针只在 needs_evidence → open 时补上。
- 三类阻塞异议提为 open 时，指针必须能核对，而且要对得上类别：
  - 来源不存在：fetch_failure / missing_source / gone；
  - 数字错误、引文不支持结论：quote。
- 只写位置（location）的指针，只能用于 needs_evidence 或不阻塞的类别。
- 指针核对：
  - quote：引文在所指来源版本的正文快照里能定位；
  - fetch_failure：用量账本里确有这条记录号，且是针对该来源的失败抓取；
  - missing_source：论断确实没有来源；
  - gone：只有规则能用，且来源当前确实是 gone。

## 4. 规则（evidence.mjs）

规则只执行，不做内容判断。写入同样经提交入口晋升，身份是 `system`（`workbench-rules`）。request_id 由内容决定，重复执行不会写两次。

- **补证**：
  - 异议处于 needs_evidence、又没有进行中的补证任务时，生成 `find_evidence` 任务。任务每个只做一次（规则内部传入 `maxAttempts: 1`，接口传不进来），所以 `evidence.maxAttempts` 数的是任务个数。
  - 用完之后仍待补证，规则把异议转为 needs_user，写明理由，不会自动作废。
- **来源已不存在**：
  - 主持人确认 gone 后，对每条（当前版本）引用它的论断提出“来源不存在”异议（open，指针 gone）。
  - 撤销 gone 时，撤回规则自己提出、还没结束、也没被裁定成立的这类异议。
  - 再次确认 gone 会再提。同一论断版本上已被核验者驳回过的，不再重提。
- **触发**：每次提交完成、每个任务结束（done / failed / cancelled）、主持人改可获取性、服务启动时，各触发一次。
  - 同一项目串行执行；执行中又被触发，就在结束后再跑一遍。
  - 出错只记日志，不影响触发它的那次写入。

## 5. 对抗核验与补证任务（modes.mjs、runner.mjs、packets.mjs）

- **新任务类型**：特殊类型 `verify_claim`、`find_evidence`。可见性按“读资料”处理：输入内联，不给工具。
- **任务包**：读资料的任务里，论断输入会带上它所引的每个来源（按引用版本）及其正文快照。
- **提示词与解析**：两种任务的提示词模板和结果解析在 `modes.mjs`，“提示词模板随 modes 维护”从这里开始。
  - 对抗核验要求找反例和证据缺口，并明确写出：“引文存在不等于支持结论”，以及 textual 论断要核对最早出处。
  - 结果是一个 JSON 对象：`verdict`、`reason`、`support_quote`、`objections[]`。runner 把它转成核验记录和异议，**目标版本和来源版本取自任务输入里的论断，不采信回复里自填的版本**。
  - 补证结果只能是对任务针对的那条异议的一次更新；回复里没有 json 代码块，就算“这次没找到”，任务失败（只做一次，所以直接 failed），由规则决定下一步。
- **派发检查**：`verify_claim` 只派给能计入份数的核验者，即与作者不同厂商、厂商推断得出、还没核验过当前版本。不合格时在认领之前就返回 409，任务保持 open。

## 6. 接口、界面与 MCP

**接口**：

- `POST /verifications`：主持人入口或 MCP 会话（带 agent）。`source_versions` 省略时，取论断当前所引的来源版本。
- `POST /objections`：提出异议。
- `POST /objections/:o/resolve`：改变状态，能否执行由状态机按身份判断。文档里这个接口只写了“裁决 needs_user”，现在泛化了。
- `POST /claims/:c/verify`（新增，只限主持人）：建对抗核验任务并派发。
  - 不指定参与者时，自动挑能计入的参与者，凑够还差的份数；
  - 指定参与者时，先全部检查、再建任务，不会建了一半才失败。
- “待你决定”新增两项：`objection_needs_user`、`claim_disputed`。

**界面**：

- 论断详情加核验面板：结论与份数、计入的核验和不计入的原因、派对抗核验、主持人核验；以及异议列表和提出异议的表单。
- 异议详情显示状态、类别、指针、提出者、处理说明，并能改变状态。
- 打开着的记录详情会随实时事件刷新；正在填表单时不刷新。

**MCP**：新增 `wetalk_verification_create`、`wetalk_objection_create`。晋升被拒时，`mcp.mjs` 把逐条原因一起交回给 Agent。

## 7. 测试

- **`contract1.test.mjs`**：契约一的 6 条验收案例逐条对应：
  - 引文存在却不支持结论；
  - 论断改措辞后旧核验失效；
  - 两条阻塞异议只解决一条；
  - 待补证 → 补证任务 → 超限转 needs_user；

  另有：核心结论两份（同一核验者只算最新一份、主持人算一份、MCP 不计入、改判后变为 disputed）、同厂商的两个参与者各算一份、核验记录的各项写入检查、异议指针规则、裁定者与撤回者的身份规则、upheld → resolved 的条件、gone 规则（提出 → 不重复 → 撤销即撤回 → 再确认再提），以及经 runner 派发的对抗核验与补证。

- **改动的旧测试**：
  - `deps.test.mjs` 的夹具给论断和核验补上身份；没有身份的核验现在不计入，这是本次的设计。
  - `commit.test.mjs` 里“核验与异议在 WP5 之前被拒”的断言，改为格式错误、临时编号、自报 verifier 被拒。

## 8. 已知限制与请你重点看的地方

1. **厂商来自配置，不是实际报告**：任务持有者的厂商由服务端配置的适配器和模型推断。Claude、Codex 的 CLI 实际报告的模型记在调用记录里，但没有拿来校正身份。配置写错（例如 generic 适配器的模型名写成别家的），身份就会错。
2. **普通读资料任务也能写核验记录**：抽取任务的结果里也可以夹带核验记录，跨厂商与引文规则照样检查，身份就是任务持有者。我认为这可以接受（这确实是那个参与者的判断），但请你判断是否要限定只有 `verify_claim` 任务和主持人能写。
3. **补证名额会被技术失败吃掉**：补证任务调用失败（超时等）也算用掉一次补证名额。
4. **disputed 不会自动升级**：结论不一致的论断只进“待你决定”，规则不会自动生成 needs_user 异议。
5. **都需要主持人手动派发**：自动调度在 WP6；规则只建补证任务，不派发。
6. **“作者”指当前版本的内容来源**：异议的“作者”取目标版本的 provenance。人工修订会保留原内容的来源关系（文档要求），但当前代码里，主持人改过的版本，作者记为主持人。
