## 本轮 R1 · 密封调用失败的正文进了用量账本 → 已修复

上轮只清理了调用记录和任务历史，漏了 `usage.settle()` 这个出口。这次改为一个入口、一条规则：

- **CLI 调用**：`execute()` 的 catch 先按可见性得出可以落盘的报错 `error`（密封类任务用 `sealedError()`），再依次写用量账本、调用记录和任务历史，三处用的是同一个值。
- **API 调用的每次请求**：密封类任务交给 DeepSeek 客户端的用量钩子先包一层 `safeHooks()`，结算行的 `error` 只保留客户端自己的类别词（parse、timeout、aborted、network），其余一律换成 `HTTP <状态码>`，没有状态码时写“请求失败”。服务端报错 JSON 里的 `message` 和非 JSON 正文都不会落盘。调用记录里 `exec.attempts[].error` 用 `safeExec()` 按同一规则清理。
- 正文断连、坏 JSON 时，客户端 `AgentError('parse')` 的消息里带着响应正文前 200 字。这条消息只会经过 `sealedError()`，parse 不在放行之列，所以同样不会落盘。

不是只在 HTTP 输出时隐藏，磁盘上本来就没有。

回归：

- 真实通用适配器输出金丝雀后以退出码 1 结束：整个项目目录（含 `usage.jsonl`）、`usage.entries()`（用量接口返回的就是它）和任务 JSON 里都没有金丝雀；账本的结算行写的是“退出码 1；密封期间不记录报错原文……”。
- 密封的 DeepSeek 任务：第一次 503 且报错信息回显金丝雀，重试一次后返回 200、正文不是 JSON 且含金丝雀。项目目录和用量条目里都没有金丝雀；账本两次结算的报错是 `['HTTP 503', 'parse']`，调用记录 `exec.attempts` 也一样。
- 上轮“成功且带工具审计参数的稿，揭晓前不落盘、揭晓后才补写”的用例保留。

探针：`usageFileLeak: false`，`usageRecentLeak: false`。

## 本轮 R2 · 揭晓先删轮次，取消或写盘失败会丢结果 → 已修复

揭晓拆成三步，密封存储的破坏性 `reveal()` 换成 `peek()`、`drop()`、`complete()`：

1. **先校验，不写任何正文。** 逐个成员查任务：
   - 已取消或已失败（cancelled、failed）的成员移出本轮，它的稿直接丢弃，从不落盘。返回值的 `dropped` 里列出这些成员。
   - 上次揭晓中途已经完成的成员跳过。
   - 其余成员必须同时满足：有结果；任务是 submitted；结果的尝试号等于任务当前尝试号；当前尝试的 `sealed_round` 就是本轮。只要有一个不满足，整轮不动，返回 409，并列出每个不满足的成员及原因（例如“T002（claimed，还没有结果）”）。迟到的旧尝试也就不能借揭晓重新进入结果（收集时的栅栏是第一道检查，这里是第二道）。
2. **逐项写盘，每一步都可以重做：**
   - 正文 blob 按内容寻址；
   - 补写调用记录前，先查这次调用是否已有 `fill_of` 记录，有就不再追加；
   - 已完成的任务不再改动。
3. **全部写成后才 `complete()`，从内存里释放本轮。** 中途任何一步抛错，轮次和没写出的结果都还在，修好故障后对同一轮再次揭晓，会从断点继续。

这次补测还查出任务看板的一个相关缺陷，已一并修复：状态转换先改缓存里的任务对象再写文件，写文件失败时缓存里是 done、磁盘上还是 submitted，重试揭晓时会把它当成“已完成”跳过。现在 `save()` 写失败时丢掉改了一半的对象，按磁盘上的版本重新读回（新建时写失败则从缓存里移除），再把错误抛出。这条对所有状态转换都有效，不只是揭晓。

回归：

- 两份稿都收集完后取消其中一份，再揭晓：被取消的稿移出本轮，项目目录里搜不到它；另一份完成为 done；再揭晓返回 404（已完成，内存已释放）；补写记录只有 1 条。
- 第一份完成后，第二份在三个不同位置各注入一次 ENOSPC：blob、`calls.jsonl`、任务文件。每种情况下：
  - 首次揭晓抛 ENOSPC，第一份为 done、第二份仍为 submitted，轮次里两份结果都还在；
  - 再次揭晓完成，第一份的结果不变、只经历一次 done 转换，第二份的正文正确，补写记录正好 2 条，轮次释放。
- 有成员还没交稿时揭晓：409 且点名该任务，先交的稿哪里都没写出、没有补写记录；交稿后揭晓成功。
- 原有密封测试里未完成时揭晓的报错文字随之更新；它原来用旧签名调用 `sealed.status('R1')`，断言会空过，已改成带项目参数并断言进度。

## 回应评审里的设计意见

- **长来源的输入内联：** 同意。WP5 起，长来源按任务挑选可追溯的片段，或者拆成多个任务；任务包照旧记下原版本、定位和实际发送的内容，不静默截断。
- **CLI 配置的模型与实际报告的模型：** 调用记录里两者已分开记（`config.model` 和 `reported.model`、`reported.vendor`）。WP5 判断厂商独立性时以服务端派生的为准，不凭显示名称或自报身份。
- **“任何磁盘文件与接口都拿不到密封稿”：** 这句话现在覆盖用量账本、API 每次请求的报错和任务状态，回归测试按整个项目目录扫描。

## 文档修订（主持人已同意，已写入 `workbench-dev-spec-v0.2.md`，开头的“本地修订”说明一并更新）

1. **契约四“密封期间不落盘”**：明确写上，占位规则覆盖所有持久出口，包括用量账本的结算行和 API 每次请求的报错（只留类别词或 HTTP 状态码）。

   - 写盘中途失败时保留轮次，可以对同一轮再次揭晓、从断点继续，不重复补写；
   - 全部写成后才释放内存。
