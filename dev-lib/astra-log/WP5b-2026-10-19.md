## 0. 范围与主持人的决定

按主持人批准的拆分，5b 做分工、竞争和研讨室整合。

- 竞争方案先由主持人选定；用研讨室的表决来选，留到以后。
- 我自己定了两件文档没写明的事，请你判断：
  - **书记是规则，不是模型。** 设计文档要求书记“只按规则应用已经通过的补丁”。用程序做，才能证明“未经通过的内容没有进入正式大纲”。
  - **评审者不能是起草者。** 起草者会认出自己的方案，匿名就失效了。

## 1. 分工（divide.mjs、commit.mjs 3c）

- `POST /divide`（只限主持人）：`{ type, title, goal, inputs: [{id, version}], items: [文本], participants: [id…], assignments? }`。
  - 只能用 `modes` 里是 `divide` 的类型。
  - 输入是记录（固定为当前版本），或文字条目（例如待找资料的子题、网址）。
  - 默认轮流分给参与者；也可以给 `assignments` 指定分配。
  - 每份一个子任务，立即派发；任务上记 `division`（编号 DV###、第几份、共几份、分到的条目）。
- **互不重叠由程序保证**：
  - 拆分时：同一项出现两次、指定分配里有项分到 0 份或 2 份、同一参与者分到两份，都拒绝，一个任务都不建。
  - 晋升时（提交入口新增“3c”步）：子任务只能写自己那一份。改动的记录、引用的记录、核验与异议的目标，都要在这一份的输入里（论断输入连同它所引的来源），或是本次新建的记录；否则判 `out_of_scope`。
  - 新建的来源卡不能与已有来源同一地址，否则判 `duplicate_source`。这条只对分工子任务生效。
- 结果照常经提交入口写成来源卡和论断。`GET /divisions` 按份列出进度，以及每份写进正式区的记录。

## 2. 竞争（compete.mjs、modes.mjs、runner.mjs）

流程记录存在 `<项目>/competitions/K###.json`。它和任务一样由服务维护、不进 git，每一步都记在 `history` 里。

阶段由任务状态派生：密封起草中 → 待发起匿名评审 → 匿名评审中 → 待你选定 → 移植补丁 → 已结束；另有“有效方案不足两份”和“已取消”。

1. **发起**（`POST /compete`）：
   - 只能用 `modes` 里是 `compete` 的类型。
   - 起草者人数必须等于 `compete.drafts`，而且不能重复。
   - 输入固定为当前版本。
   - 几份方案的任务带同一个 `sealed_group`。runner 派发其中任何一份时，同组还没结束的成员一起进同一个密封轮次。
   - 服务重启后，轮次随内存消失，任务回到 open。点“派发还没开始的成员”时按组重建轮次，所以不会一份一份单独揭晓。
2. **揭晓**：
   - 沿用 WP4 的揭晓：先校验，再逐项写盘。
   - 方案全部结束后，竞争随机分配标签（方案甲、方案乙……），之后界面和每一轮评审都用这同一套标签。
   - 独立性未证明的方案不参与比较。有效方案不足两份时只能取消。
3. **匿名评审**（`anonymous_review`，同样是密封的同组任务）：
   - **评审拿到什么**：任务输入是以标签命名的方案正文。runner 遇到全是标签的输入时，保留这套标签（不再按任务随机），照常去掉署名，在每节标题后标上〔第 n 节〕。提示词照常检查署名，有残留就拒绝发出。
   - **评审的输出要求**（modes.mjs）：
     - 每条意见指向某个方案的第几节（或第几页，按节计），或该方案里出现的论断编号；
     - 输出 JSON 数组，也可以逐行写“方案甲 第 2 节：……”。
   - **意见在一轮评审全部结束后解析并固定下来**（`parseReview`）。以下几种退回，原文和原因都保留，不交给主持人：
     - 没写位置；
     - 方案不存在；
     - 节号超出范围；
     - 论断不存在，或不在该方案里；
     - 只有位置、没有意见。
   - 独立性未证明的评审整份退回。引导语（以冒号结尾、不含标签的行）、标题行和空行忽略。
   - 标签与起草者的对应关系，在评审全部结束（待你选定）之前不出现在竞争接口里。
   - 评审全部失败或被取消时，可以再发起一轮。
4. **选定**（`POST /competitions/:k/select`，必须写理由）：
   - 选定的方案原样写成正式作品：大纲；核心解释写成讲稿。
   - 内容来源是起草那次尝试的身份（`board.identityOfAttempt`，含实际报告的厂商），`basis: compete-selected`，另记竞争编号和选定者。选定它的主持人不是作者。
   - 作品的 `claims` 取正文里提到、且在任务输入里的论断，版本按输入。这些论断在起草之后改过版时，提交入口按 `stale_dependency` 拒绝，候选稿保留。
5. **移植补丁**（`POST /competitions/:k/patches`，主持人或 MCP 会话；MCP 提出的补丁，提出者记为未证实）：
   - 格式：`{ from: { draft, section, quote? }, to: { section, position }, note?, comment? }`，position 取 before / after / start / end / replace。
   - 只能从落选方案搬运整节，或其中逐字的一段（按引文定位规则找到后，取原文里的确切字符）；节号按底稿原来的分节。
   - 搬运的原文在提出时就存进补丁（`content`）。书记应用前会再核对一次，必须一致。
6. **接受或拒绝**（只限主持人）：
   - 每条补丁都留记录：谁、何时、理由。拒绝必须写理由，决定后不再改。
   - 冲突的补丁不能同时接受：整节替换的那一节，不能再有别的替换或节首、节尾插入。
7. **书记**（`POST /competitions/:k/apply`，规则 `workbench-scribe`）：
   - **怎么生成**：底稿（选定的方案原文）加上全部已接受补丁（按编号），得到作品的新版本。
   - **底稿不改**：除了补丁搬来的原文和分隔用的空行，其余字符原样保留；整节替换的那一节例外，替换同样要经主持人接受。
   - **作者**：作者集合并上被搬运原文的起草者。提交入口新增内部参数 `carryAuthors`，只供服务内部流程使用，不从请求体取。
   - **不覆盖别人的改动**：书记只在自己上次写的版本上继续。作品在竞争之外被改过时，提交入口按 `version_conflict` 拒绝，书记不覆盖。这时竞争照样可以结束，没应用的补丁标为 skipped 并记下原因。
8. **少数意见记录**（选定之后在竞争视图里）包括：
   - 被拒的补丁（含理由）；
   - 接受了但没应用的补丁；
   - 没被任何已接受补丁采纳的评审意见；
   - 落选方案（原文在 blob 里）。
9. **结束与取消**：
   - 结束：要求没有待决定的补丁，已接受的都已应用（作品在竞争之外被改过时除外）。
   - 取消：只在选定之前，进行中的任务一起取消。
10. **并发**：同一个竞争的改动排在一个队列里逐个执行：发起评审、重新派发、选定、补丁、书记、结束、取消。选定和书记要等提交入口晋升，写完后重新读一遍竞争记录再保存。
11. **待你决定**：列出每个竞争下一步要你做的事：揭晓、派发、发起评审、选定、决定补丁、应用、取消。

## 6. 已知限制与请你重点看的地方

1. **表决选择没有做**：主持人已决定以后再接。
2. **补丁只由主持人或 MCP 会话提出**：还没有“派一个 Agent 任务批量提补丁”的流程（结果需要绕开提交入口写进竞争记录，打算放到 WP6 再做）。
3. **对应关系只对评审隐藏**：主持人在任务列表里看得到每个起草任务的持有者和结果，能自己对上标签。匿名保护的是评审拿到的内容；竞争视图在评审结束前不给对应关系，只是界面上不剧透。
4. **“节”的定义**：
   - 按 Markdown 标题分节：最小的标题级别；它只出现一次、又是第一个标题时，取下一级。
   - 没有标题的方案全文算第 1 节；“页”按节计。
   - 起草要求里写明了用二级标题分节。
5. **意见格式**：逐行格式要求标签紧跟位置；一条意见写成多行时，后面几行会被当成没有位置而退回。JSON 格式没有这个问题。
6. **作品引用的论断**：起草之后论断改了版，选定会被提交入口拒绝（`stale_dependency`），只能取消重来。我认为这符合契约二“过期的结果不直接发布”，但会让人觉得严格。
7. **书记不变基**：作品在竞争之外被改过之后，书记不再应用补丁，剩下的补丁只能手工合并。
8. **读竞争时会写文件**：第一次读到“方案全部结束”时分配标签，第一次读到“一轮评审全部结束”时固定意见，都会写竞争文件。标签只分配一次；意见解析是确定的。
9. **分工条目的重叠只按文字判断**（去掉首尾空白、压缩空白、不分大小写）。意思相同但写法不同的子题，程序判断不出来。
10. **一次没能复现的测试失败**：
    - 有一次全量运行报了一条 `assert.ok` 失败，输出被截断，没看到是哪一条。
    - 之后连跑 3 次全量（181/181）、4 次两个新测试文件（13/13），都通过。
    - 我把“全部交稿前不能揭晓”那条测试里按时间等待的时限，从约 1 秒放宽到 10 秒，因为它最依赖调度时机。
    - 如果你在复审时遇到失败，请告诉我是哪一条。
11. **工坊页面没有英文**：研讨室的新文字有英文，工坊页面仍只有中文。

## 7. 文档修订（待主持人同意，同意后写入 `workbench-dev-spec-v0.2.md`）

1. **目标结构与契约二“其他约定”**：
   - 模块清单新增 `compete.mjs`（竞争流程）、`divide.mjs`（分工拆分），`modes.mjs` 负责提示词模板、分节、评审意见检查与补丁应用；
   - 项目目录新增 `competitions/K###.json`（竞争的流程记录，服务维护，不进 git），projects 仓库的忽略规则加上它。
2. **数据模型“内容来源”**：
   - 竞争选定的方案写成作品时，内容来源是起草那次尝试的身份，另记选定者；
   - 书记（规则）写的版本，作者集合并上被移植原文的起草者；
   - 规则与抓取不写进作者集合。
3. **契约三**：任务新增内部字段 `competition`、`sealed_group`、`division`，只由工坊内部流程填写；同组的密封任务进同一个密封轮次，重启后按组重建。
4. **WP5“分工”**：互不重叠的检查规则：拆分时每项恰好一份；晋升时拒绝越界写入（`out_of_scope`）和重复的来源地址（`duplicate_source`）。
5. **WP5“竞争”**：
   - 标签在方案全部揭晓后统一分配，评审者不能是起草者；
   - “具体位置”的定义（节按 Markdown 标题、页按节计、论断须在该方案中出现）与退回规则；独立性未证明的评审整份退回；
   - 选定由主持人进行并写理由，表决以后再接；
   - 移植补丁的格式、冲突规则，拒绝须写理由、决定后不改；MCP 会话可以提补丁（未证实）；
   - 书记是规则：只应用已接受的补丁，只在自己上次写的版本上继续，不覆盖竞争之外的改动；
   - 少数意见记录的内容。
6. **接口清单**：
   - 新增 `GET /divisions`、`POST /divide`；
   - 新增 `GET /competitions`、`GET /competitions/:k`、`POST /competitions/:k/reveal | dispatch | review | select | patches | patches/:x/decide | apply | close | cancel`（`POST /compete` 原有）；
   - SSE 新增 `competition` 事件（不带正文）；“待你决定”新增竞争事项。
7. **研讨与工坊**：议题可挂项目（`project`、`ref`），`GET /api/threads?project=`；挂了项目的议题，记忆默认用“工坊·项目名·研讨”空间，WP6 引入阶段后改为按阶段。
