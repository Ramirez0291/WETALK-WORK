## R1 · 调用次数并发越过硬上限 → 已修复

`usage.mjs` 改为“先占用、后结算”：

- 每次物理请求发出之前，`reserve()` 在**同一个同步步骤里**检查上限并占用一个名额，同时把 `{id, phase: 'start'}` 写进 `usage.jsonl`。结束后 `settle()` 写 `{id, phase: 'end', ok, status, usd, …}`，只结算，不再计数，同一 id 只结算一次。
- 调用次数 = start 行数，包括正在进行的请求和中途退出、没来得及结算的请求，所以是硬上限。服务在发请求之后、收到响应之前退出时，重启后这次尝试照样计数（保守）。
- 费用 = end 行的 usd 之和，仍是软上限（主持人已批准）。补充说明：并发时的超出量最多是在途请求的费用之和，见 `usage.mjs` 文件头注释。
- `entries()` 把每次尝试的 start 与 end 合并成一条，没结算的带 `settled: false`。

回归用例：

- `calls=1` 时并发 3 次 Search 加 2 次 Fetch：只有 1 次成功，其余返回 429，上游只收到 1 个请求。
- 并发调用各自重试（`calls=4`）：上游正好 4 次，账本记 4 次。
- 只写了 start 的尝试在重新加载账本后照样计数，并且挡住后续占用。

## R2 · Fetch 把 B 的正文归到 A 的地址 → 已修复

抓取与来源卡的地址绑定：

- 给了 `source_id`：从**来源卡自己的地址**抓。`url` 可以省略；给了就必须与来源卡地址一致（只做 URL 规范化：协议与主机大小写、默认端口）。不一致返回 400，请求不会发出。
- 来源卡没有地址（书目类）：不能直接抓，返回 400。要补地址，走迁址。
- **迁址** `relocate: true`：只接受主持人入口（HTTP 层把 `actorOf(req)` 传进来）。改从新地址抓，正文与地址一起更新，新版本的 provenance 是主持人。系统身份和 Agent 一律 403。
- 只有与来源卡地址绑定的抓取才带 `source_id` 记账，因此只有它会影响可获取性。不绑定来源的抓取失败，不计入任何来源。

回归用例：

- 不同 path、不同 host、多了查询串，都是 400，且都没有发出请求。
- 规范化后同址（`https://EXAMPLE.org:443/A`）可以抓；省略 url 时从来源卡地址抓。
- 迁址：非主持人 403；主持人迁址后地址、版本、provenance 正确。
- 书目来源不能直接抓。
- B 的失败只影响 S001，不影响 S002；不绑定来源的失败不计入任何来源。

## R3 · 重试绕过账户 QPS → 已修复

- 限速器移进客户端：`createDeepseekClient({ rateLimits: { search, fetch } })`。每次物理请求（含重试）都先 `take()` 一个名额，再占预算名额，再发请求。服务端只建一组，所有项目共用。
- `take(signal)` 可被中止：等待名额的时间也算进总时限，“停止”同样能打断。`createWebTools` 不再自带限速器。

回归用例：

- 用真实计时：5 个并发 Search 先全部 503 再重试成功。上游共 10 次请求，任意相邻 6 次之间都间隔 ≥ 990ms，也就是任意 1 秒内不超过 5 次。
- 等待名额时被中止，立即返回。
- 名额被占满时，100ms 的总时限到点返回 timeout，请求没有发出。

## R4 · 项目 retry 覆盖对 Web 调用无效 → 已修复

- `request()` 新增 `retry` 参数。Web 的每次逻辑调用都传入项目当时生效的 `config.retry`（快照），不修改共享客户端。账户级的 baseUrl、价目和 QPS 仍然共享。

回归用例：

- 项目 `retry.max=0`：503 只发 1 次。
- 两个项目同时调用：一个重试 2 次（共 3 次请求），一个不重试（1 次），互不串扰。

## R5 · 200 头之后正文断连被当成 parse → 已修复

- 读正文（`res.text()`）抛出的异常，与连接阶段的异常同样处理：中止或超时就直接抛出，不重试；其他情况一律按网络错误重试。只有完整读到正文、并且状态码是 2xx，才进入解析。
- 完整收到但不合法的 JSON 仍是 parse 错误，不重试。

回归用例（真实本机 HTTP 服务）：

- 200 加保活空行后断连：重试成功，共 2 次请求，第一次记为网络错误。
- 503 正文写到一半断连：按网络错误重试到上限。
- 完整的坏 JSON：parse，只发 1 次。
- 超时：只发 1 次。
- 中止：只发 1 次。

## R6 · 无正文的 Fetch 把来源标为 available → 已修复

- `request()` 新增 `validate(data)`：HTTP 200 且 JSON 合法之后的业务检查。
  - Fetch：`content` 必须是非空字符串（去掉空白后）。
  - Search：必须有 `results` 数组。
- 检查不通过时，这次尝试以 `ok: false, status: 200, error` 结算（不计费），抛 `invalid`，不重试，Web 层把 Fetch 的 invalid 映射为 404。可获取性只看结算结果，所以这种失败不会让来源恢复为 available。

回归用例：空串、全空白、缺 content、content 为数字四种情况，HTTP（404 / invalid）、账本（ok:false, status 200, usd 0）、可获取性（temporarily_unavailable）三者一致；来源不升版。

## 你在“回应设计问题”里提的一项：正文快照的来源约束 → 本轮一并做了

你指出 blob 目录里也有记录 JSON 等内容，“blob 存在”不等于“它是正文”。新增 `snapshots.mjs`，在 `<项目>/snapshots.jsonl` 登记正文快照：

- `origin: 'fetch'`：url、标题、时间，`service: 'deepseek-fetch'`，注明是第三方服务返回的 Markdown，不保证与网页逐字一致；
- `origin: 'manual'`：主持人录入，记录录入人。

来源卡的 `text_blob` 只能指向登记过的快照；指向记录 JSON 等其他 blob 返回 400。追溯视图的来源节点带 `snapshot`（来处、url、服务），核验者能看到这份正文是怎么来的。

回归用例：

- 用论断记录的 blob 冒充正文：被拒；
- 主持人把同一份 Fetch 快照挂到另一张来源卡：可以；
- 追溯显示 fetch 来处；
- 主持人录入的正文登记为 manual 并记录录入人。
