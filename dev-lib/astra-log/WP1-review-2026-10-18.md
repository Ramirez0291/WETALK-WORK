## R1 · P1 · Git 路径没有按字面值处理，会提交其他项目的修改

位置：`lib/workbench/git.mjs:47–49`。

`git add -- <paths>` 和 `git commit -- <paths>` 的 `--` 只结束选项解析，路径仍按 Git pathspec 匹配。项目名校验允许 Windows 合法的方括号，因此这个错误可以从正常的新建项目入口触发。

复现：先创建 `文稿a`，给其 `project.md` 追加一行未暂存修改，再创建 `文稿[ab]`。后者返回留档成功，但新提交包含：

```text
文稿[ab]/baseline.md
文稿[ab]/project.md
文稿[ab]/protocol.json
文稿a/project.md
```

最后一项不属于本次项目。违反契约二“只提交本次清单里的路径”，也会把主持人尚未准备好的其他项目修改留档。

建议：add 和 commit 两处均启用 Git 的字面路径模式（如全局选项 `--literal-pathspecs`），或逐路径构造 literal pathspec。不要只处理 shell 转义；当前没有经过 shell，问题在 Git 自身的路径解释。补回归用例，确认其他项目修改既不被提交也不被暂存，并保留现有无关已暂存文件的用例。

## R2 · P2 · 新建项目的自动留档忽略项目级配置

位置：`lib/workbench/project.mjs:199–204`。

创建阶段已经验证模板里的 `protocol.json`，但是否留档却读取 `defaults.git.autoCommit`，而不是合并后的生效配置。使用含 `{"git":{"autoCommit":false}}` 的项目模板新建项目后，返回的 `project.config.git.autoCommit` 为 false，实际 HEAD 仍新增一个项目提交。全局 false、项目 true 的方向也被同一分支忽略。

建议：使用新项目的有效配置决定是否留档；保留明确的 skipped/disabled 状态供 HTTP 和 CLI 使用。目前返回时丢弃 `skipped`，CLI 会把跳过留档显示为“完成”，也应一并修正。测试覆盖两个方向的覆盖和跳过状态。仓库初始化的 `.gitignore` 提交可单独定义，不要与项目留档混淆。

## R3 · P2 · 配置合并绕过了部分类型校验

位置：`lib/workbench/project.mjs:59–73`。

两条分支实际比交接说明承诺的“类型必须与默认值一致”更宽松：非 null 默认值也能被 null 覆盖；OPEN_MAPS 新键直接写入、完全跳过值类型检查。当前以下配置全部被接受并由 `get()` 返回为有效配置：

```json
{"git":{"autoCommit":null}}
{"export":{"formats":null}}
{"modes":{"custom":42}}
{"routing":{"custom":"claude"}}
```

这让调用方无法依赖这里返回的类型；尤其是新增任务类型恰好是 OPEN_MAPS 支持的正常用法，却与现有键的值类型规则不一致。后续模块会收到空数组字段、数字工作方式或字符串路由，而不是明确的配置错误。

建议：null 仅允许在明确可空的字段；开放映射只开放键名，值仍校验（modes 为合法工作方式，routing 为字符串数组）。为这些反例补测试。`rounds`、`export.template`、`export.skill` 当前默认 null 不代表所有 JSON 类型都具有业务意义，后续补明确字段 schema；不要依靠默认值推断全部约束。

## 回应主程的设计问题

### 配置策略

未知键报错合理；modes/routing 可增加任务类型也合理，前提是修复 R3 的值校验。以后修改协议时，仍需按文档写 decisions 记录并将生效配置快照放入任务包。当前不要求为 WP1 提前实现协议编辑器。

### 作者身份（WP2/WP4）

赞同提交入口派生身份，但必须来自服务端保存的任务尝试及可信调用记录，不能直接相信请求里的 author、holder、model 或 vendor 字段。身份应按记录版本存储，包含主体、实际模型/厂商、task/attempt 及来源依据；同一任务重试或切换模型时不能沿用旧身份。

`source.author` 已表示文献作者，建议用独立的 `created_by` / `provenance` 字段表达内容生产者，避免同名混淆。后续人工编辑、移植补丁也要保留来源关系，不能仅用最后提交者覆盖内容来源而绕过跨厂商核验。

人类提交应有明确的 human 类型和受控入口；不能把“请求声称我是人类”当作身份。MCP 外部会话要绑定服务端登记的主体与租约；无法证明实际模型/厂商时记录为 unknown/unverified，不能因填写了一个不同厂商字符串就计入独立核验。人类核验如何计数需在契约一明确，而不是把 null 厂商自动视为“不同厂商”。WP2 尚无完整 WP4 时，可用受控的人工路径或最小服务端身份结构，避免用可伪造字段填补空缺。

### Windows staging + rename

同一 projects 根目录内先 staging 再 rename 的方案适合 WP1；现有忙碌重试和失败后清理方向合理。本轮未证实除此之外的目录替换缺陷，不把沙箱 EPERM 当作实现错误。

WP2 必须让新建项目、晋升和 git 留档统一服从仓库级队列与实例锁；只锁晋升不够。CLI 的 fetch 任意失败不能证明服务已经退出（连接中断时服务可能已完成写入），本地回退应先验证仓库锁。目标目录竞态最终冲突应转成明确的 409。残留 staging 的恢复/清理须在持有锁后做，不能删除仍在使用的目录。上述是已声明后续范围的集成条件，不重复列为本轮缺陷。
