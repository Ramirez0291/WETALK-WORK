## R1 · P1 · prepared 之后写入失败，必须恢复或阻止后续写入

位置：`lib/workbench/commit.mjs:355–356`；关联 `lib/workbench/txn.mjs` 的队列错误处理和 `recover()`。

当前 `txn.apply()` 抛错后，请求失败，但队列会继续处理下一个请求，已持久化的 prepared 清单保留到下次启动。对于“文件被占用、重试耗尽”等不会结束服务的异常，旧事务可能在后来成功提交之后才被恢复，倒序覆盖新数据。

实际复现使用 `fs.renameSync` 故障注入：对目标 `S001.json` 的替换持续抛 EPERM，走完现有 8 次重试后恢复正常文件操作，没有强杀进程：

1. 已有 `S001 v1`。
2. 提交 000002 尝试写入内容 A；清单已 prepared，替换失败，API 对应调用抛错。
3. 服务继续运行，另一提交 000003 成功把同一来源从 v1 更新为 v2，内容 B，并返回 applied。
4. 重启恢复 000002 后，正式文件变成内容 A；已确认成功的 B 被覆盖。`inbox` 仍为空。

这不是“失败请求可以被重做”的问题，而是已成功提交的后续结果被早先失败事务覆盖。

修复要求：一旦存在 prepared 但未完成的事务，必须先在同一仓库临界区完成恢复，再接收后续晋升；无法恢复时应进入明确的故障状态，阻止继续修改正式区。也可使进程停止提供写服务并要求重启恢复。不能仅捕获异常后继续队列。补测 EPERM 重试耗尽、ENOSPC/日志追加失败等非退出异常，断言后续成功提交在再次重启后仍保留。

## R2 · P1 · 删除正式文件后会复用旧编号，旧引用静默指向新来源

位置：`lib/workbench/commit.mjs:242–255`（`nextNumbers()`）。

新编号只根据当前记录和当前目录文件名计算，没有保留 applied 历史中已用过的编号。删除最大编号文件后，它就重新变成可分配编号。

复现：先提交 `S001 v1` 和引用它的 `C001`；外部删除 `S001.json`，此时 inbox 正确报告删除。再正常新建一条完全不同的来源：

```text
新分配编号：S001 v1
inbox：[]
C001 新鲜度：current
C001 追溯到的来源：新建的无关来源
```

新事务覆盖了 `lastBlob` 的含义，删除告警消失，旧 `{id:S001, version:1}` 引用被重新解释为另一份证据，破坏身份与版本唯一性。

修复要求：分配编号时将提交日志和待恢复事务中出现过的编号纳入保留集合，不能只看存活文件。删除恢复必须保留原身份；普通“新建”应得到未使用的新编号，或在待处理删除冲突时明确拒绝。补测删除最高编号、删除全部同类记录、重启后再新建，确认旧下游仍待处理，不能自动变成 current。

## R3 · P1 · 日志尾部修复使内存与磁盘不一致，并删除唯一恢复清单

位置：`lib/workbench/txn.mjs:117–135`；调用顺序见 `lib/workbench/commit.mjs:54–55`。

`createCommitLog()` 先按 JSON 是否可解析建立索引，包括“JSON 已完整、但最后换行未写入”的尾行；随后 `repairTail()` 无条件删除无换行的尾行，却没有同步清除或重建内存索引。恢复流程因此把磁盘已删除的 applied 当成仍存在，删除对应 `_txn` 清单。

复现：在 applied 注入点停止一次提交，保留清单；移除日志最后一个换行字节，模拟尾部短写，再重启：

```text
内存 applied：000002、000001
重新从磁盘加载 applied：000001
_txn：空
再次重启：000002 消失，正常的 S001 v2 被报成 external_change
```

修复要求：先规范化磁盘尾部，再建立全部内存索引。对完整 JSON 的无换行尾行，可以验证后补换行，或截断并依靠清单重做；必须确保内存、磁盘和恢复采用同一决定。补测仅缺换行、JSON 中途截断、applied/archived 不同状态尾行，并连续重启两次检查提交数和清单，不能只验证第一次启动成功。

## R4 · P1 · 两个进程接管旧锁时，都可能认为自己持锁

位置：`lib/workbench/txn.mjs:85–88`（检查旧 PID 后直接删除锁文件）。

新建锁用 `wx` 能防止同时创建，但失效锁的删除不是原子的条件删除：A 读取旧持有者并认定它已退出；B 此时清理旧锁、创建新锁；A 随后删除的是 B 的新锁，再成功创建自己的锁。A、B 都继续运行，单写入者约束失效。

复现脚本通过现有 `isAlive` 注入点确定性模拟该交错：在 A 已读旧锁的存活检查中，让 B 先完成接管，再恢复 A。结果两个 `acquireLock()` 都成功返回且 token 不同，磁盘最后只记录 A。这里验证的是可发生的并发交错，不声称进行了大规模多进程压力测试。

修复要求：使失效锁的接管过程本身具有跨进程互斥保证，不能凭一次过期的读取直接 unlink 当前锁。单纯“删除前再读一次 token”仍有检查与删除之间的竞态。增加确定性交错用例及实际双进程在遗留旧锁下启动的用例，必须只有一个持有者能进入初始化/恢复/写入阶段。

## R5 · P2 · 依赖只查版本，未采纳的外部修改可被新提交引用

位置：`lib/workbench/commit.mjs:311–315`；对比仅检查修改目标的 `:280`。

被修改目标会验证 `lastBlob`，但仅作为依赖的上游没有同样的检查。正式来源被外部修改而版本号不变时，基于它的新论断可以晋升，并被标为 current；追溯直接展示这份未被提交入口采纳的内容。

复现：提交 `S001 v1` 后直接修改其 title、保持版本为 1，再提交新论断引用 `S001@1`。晋升成功，论断 freshness 为 current，追溯 title 是外部改后的值，inbox 同时保留 external_change。也就是说，同一个版本已经有两套不同内容，一套在 applied blob，另一套进入新追溯链。

修复要求：在晋升临界区验证所使用依赖的内容与已提交版本一致（包括需要使用的上游链），或从已提交的不可变快照解析依赖并明确隔离外部改动。不能把工作区的同版本号自动等同于已提交版本。补测上游同版本修改、无 applied 的外部新增来源；未经采纳的内容不得成为正常晋升的依据。

## 对主程三个问题的答复

### 1. 外部改动检查的顺序是否误伤

目标版本检查旁边验证 hash 的位置合理，正常完整恢复后 hash 应一致。但本次发现的 R1、R3 说明“启动恢复一定得到一致状态”尚未成立；应先修复它们。R5 则是检测范围不够：不能只保护写目标，遗漏参与晋升的依赖。

### 2. update-ref 旧值校验与按编号留档是否足够

这是正确的基础：临时索引、按 blob 字节构建、带旧 HEAD 的更新，比读取当时工作区更可靠；现有字节一致性及无关暂存文件测试也通过了。但它只能约束那一次 Git 更新，不能补救正式区恢复顺序出错。R1 的旧事务后来被重做，会使正式区最终内容与较新提交的 blob 不一致；再加上 R4 的双写入者风险，目前不能保证“每个路径最后留档版本等于正式文件”。

修复后请补验“留档失败累计多个提交 → 服务重启 → 恢复留档”，逐次核对提交对应的确切 blob 和最终正式文件，不只核对最后一次 HEAD。启用 `git.autoCommit=false` 或存在待留档/外部改动时，本来就不能宣称 Git 与正式区实时一致，应按状态表述。

### 3. 核验与异议写入推迟 WP5 是否可接受

接受该分期：在跨厂商和异议状态机尚未实现时拒绝 V/O 写入，比提前开放不受约束的接口合理。WP2 可以验收纯派生逻辑和其读取界面，不应把它等同于契约一已通过集成验收。

WP5 必须补齐有效身份、独立核验份数、绑定版本、支持引文和异议处理的端到端验证。尤其当前 `derive(records)` 不接收项目配置，`ready` 仅检查存在 supported 结果，尚未落实 `verify.coreClaimVerifiers` 的份数要求；接入实际核验写入前需一起实现，不能仅新增一个写接口。
