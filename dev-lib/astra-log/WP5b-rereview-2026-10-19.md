## R2-followup · P2 · pending 期间仍可接受新补丁，使原书记操作无法再重试

位置：

- `lib/workbench/compete.mjs:425–429`：`propose()` 读取并尝试补齐 pending 后，没有 `assertNoPending`。
- `lib/workbench/compete.mjs:453–459`：`decide()` 同样没有 pending 检查，继续接受新补丁。
- `lib/workbench/compete.mjs:480–484`：`apply()` 根据**当前全部已接受补丁**重新计算 request_id，再要求它等于 pending 的 request_id。

开发文档第 448 行要求：收了稿却确认不了结果时保留 pending，只允许原样重试同一个动作，其他会改竞争的操作一律拒绝。本轮实现拦住了换选、再评审、结束、取消，但漏掉了提出补丁和决定补丁。

复现步骤（只使用临时项目、模拟模型输出与故障注入）：

1. 正常选定底稿 OL001@1，提出 P1 并接受。
2. 在书记 `receive()` 已成功、`promote()` 尚未执行时模拟中断。此时候选稿已存在，`requestOutcome` 为 `unknown`，竞争持久化的 pending 对应 `[P1]`。
3. 调用正常的提出补丁和接受接口逻辑：新增 P2 并接受。**两步均成功**，pending 仍为 `[P1]`，已接受集合变成 `[P1, P2]`。
4. 再调用书记：新请求编号取决于 `[P1, P2]`，与 pending 不同，被 409 拒绝。结束竞争同样 409。
5. 停止并重新创建实际提交入口，执行 `start()` 恢复，再创建竞争实例。恢复结果 `redone: [], dropped: []`；原候选稿仍为 `unknown`，OL001 仍为第 1 版，再次应用仍 409。

探针关键输出：

```json
{
  "pendingPatches": ["P1"],
  "acceptedPatches": ["P1", "P2"],
  "applyError": {
    "message": "上一个操作（书记应用补丁）的结果还没确认：只能原样重试它，或等服务重启恢复后再操作",
    "status": 409
  }
}
```

实际影响：普通页面/API 已没有完成原样重试的路径。`apply` 不接受显式指定旧补丁集合；补丁接受后不能撤销；候选稿入口也因新加的 owner 规则不能代为晋升。重启只恢复已有事务日志，不会自动晋升这份尚未开始晋升的候选稿。用户按提示重试或重启都无法解开，需要人工修数据或调用内部入口。

修复建议：在 `propose()`、`decide()` 的 `load()` 后、任何修改前按同一规则拦截未解决的 pending；恢复路径不要依赖可变的后续补丁集合。对于已经落入此状态的数据，考虑按持久化 pending 对应候选稿恢复，而不是要求用户改文件。不要通过放开 owner 或跳过 pending 检查解决，这会破坏本轮已经修好的提交一致性。

建议补充回归：

- `pending.action === 'apply'` 且结果为 unknown 时，提出新补丁以及接受/拒绝既有 proposed 补丁均返回 409，竞争记录不变。
- 恢复正常提交入口后，原 `apply` 可重试完成一次；之后才能继续 P2。
- 重启实际 gateway 后也可原样重试；不要只新建竞争 wrapper，再手动带 owner 晋升候选稿作为唯一恢复验证。
- 覆盖已有 `[P1]` pending 与 `[P1,P2]` accepted 不一致记录的恢复方案（如决定支持修复前数据）。
