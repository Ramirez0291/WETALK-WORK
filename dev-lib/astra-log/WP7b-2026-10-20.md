## 1. 渲染检查记录 `RC###`（逐页的视觉检查）

- **记录种类**：新的正式记录 `render_check`（`render_checks/RC###.json`），每页每次一条，只增不改；改判就再写一条，以最新的为准。
- **字段**：
  - `export`：导出的哪个版本，即带这次渲染结果的那一版；
  - `render`：那次渲染的目录名；
  - `page`、`slide`：第几页、对应哪条幻灯片记录的哪个版本；
  - `image`：审的那张截图，存成 blob，随记录进 git；
  - `stage`：`initial`（模型初查）或 `final`（主持人终审）；
  - `verdict`：pass / fail；
  - `issues`：问题，kind 取 overflow / overlap / font / chart / image / readability / other；
  - `note`；
  - `reviews`：终审针对的那条初查。
- **检查者**：`reviewer` 由提交入口按服务端认定的身份填写（系统字段），组装任务包时和其他生产者身份一样剔除。
- **晋升时的规则**（`export/review.mjs`）：
  - 终审只能由主持人写；初查只能经任务由模型提交；
  - 导出必须是当前版本，渲染、页码、幻灯片、截图都要和那一版的渲染结果一致；
  - `reviews` 必须是同一版、同一页的初查；
  - 写入后不能修改。
- **失效**：上游是导出记录。重新渲染（导出升版）后，旧的检查不再算数。

## 2. 模型初查（看截图）

- **任务**：导出详情里点“派它做视觉初查”，为这次渲染建 `render_review` 任务。
  - 每批最多 8 页，一批一个任务。
  - 这类任务只由导出流程发起，手动新建会被拒绝（400）。
  - 可见性是新的 `visual`：输入内联、不给工具。
- **输入**：
  - 提示词里内联每页的文字（去掉编号与标记）和程序检查查出的问题；
  - 截图作为图片附上：执行时从 blob 取到临时目录，用完删掉；
  - 任务包记下每张图的 blob（`attachments`），可以还原。
- **输出**：一个 JSON：`{"pages":[{"page","verdict","issues":[{"kind","note"}],"note"}]}`。
  - 每页正好一次；fail 时必须写出问题。
  - 不合规时这次尝试失败，并写明原因。
  - 合规时每页一条初查记录。导出版本、渲染、页码、截图一律取自任务，不采信回复。
- **适配器**（`lib/agents.mjs` 的 `attachments`）：
  - **Claude**：带图片时改用 `--input-format stream-json --output-format stream-json --verbose`。一条用户消息里放文字和图片（base64），读最后一条 `type: result` 事件，字段和 json 输出相同。照旧 `--tools ""`、`--strict-mcp-config`。
  - **通用适配器**：把图片路径写在提示词末尾，测试和自带脚本用。
  - **Codex**：本机 PATH 上找不到 Codex，`--image` 参数没法实测，这一版不接。
  - **DeepSeek**：接口不收图片。
  - **agy**：本来就不接工坊任务。

## 5. 试运行报告

“报告”标签页（`GET /report`，可以下载 Markdown）用最新的可交付导出；没有可交付的导出时，用最新的导出并注明。报告与 `baseline.md` 的“指标”表逐项对比：

| 指标 | 怎么得出 |
| --- | --- |
| 核心论断可追溯到有效证据的比例 | 程序算：成品引用的核心论断（`core: true`）里，同时满足这三条的条数——引用的版本仍是当前版本、可进入成品、每条引文都能在来源正文快照里找到。没有标核心的，就按成品引用的全部论断算，并注明 |
| 发现的实质错误数 | 你填抽查结果（条数与清单）。程序另列流程中拦下的问题作参考：成立的阻塞异议条数、核验判为不支持的次数 |
| 你的修改时间 | 你填（分钟） |
| 总用时 | 程序算：从项目第一次提交，到成品可交付（最后一页终审的时间；只有 Markdown 时为导出时间） |
| API / 订阅额度花费 | 程序算：用量账本的调用次数、API 费用，以及每位参与者各调用了几次（命令行 Agent 的订阅额度只能按次数计） |

你填的数值存在 `<项目>/trial.json`（服务维护，不进 git），只有主持人能写。

## 6. 整套流程的集成测试

`wp7b.test.mjs` 的“集成”一项，用开发文档要求的固定样本（2 份来源、3 条论断、2 页幻灯片），在路径含日文字符的临时目录里走完下面的流程（渲染用假渲染器，看图用假参与者）：

1. **提交**：主持人录入两份来源；DeepSeek（任务身份）抽出 3 条论断，其中 2 条核心；Claude 核验 3 条，主持人再核验 2 条核心论断（核心论断要两份）；主持人写两页幻灯片。
2. **追溯**：从第 2 页追到县志原文的位置，引文找得到。
3. **更正来源**：县志的正文快照更正为 v2。下游的论断和页面变成待更新；这时导出，结构检查不通过、不可交付。
4. **重新核验**：论断改为引用 v2（升版后核验状态回到未核验），再核验；页面改引新版本，可进入成品。
5. **导出、渲染、视觉检查、终审**：导出 md 和 pptx，结构检查与读回核对通过 → 渲染检查通过 → 模型初查 2 页 → 主持人终审 2 页 → 可交付。Markdown 脚注是 `C002@2`，来源标题是更正版的。
6. **报告**：两条核心论断都可追溯（2/2）；追溯显示论断 v2 引用来源 v2，引文找得到。
